# R07：本机真实调度验证

**真机复现了“目标更快，同行反而多等”，也发现观测本身会改变时序。** 深恢复不是一概拖慢或加快同行：只恢复会拉长一次暂停，接着续算则可能因省下计算而弥补。现有本机接口只支持验证这些机制及强制动作效果，尚不能完整执行冻结策略；16 层衍生模型也没有通过流式可用性留出。

这是对**同一真实服务中的恢复动作**做配对，不是让 `entry-replay` 接管。前序 CPU 回放的离线最优仍只适用于其执行语义。[分线预登记](archive/r07-process/r07-live-preregistration.md) · [反常点登记](archive/r07-process/r07-anomaly-register.md)

## 做了什么

本机 RTX 4060 Laptop，Vulkan1，`llama-server` b10923 (`8a56aedd6`)，两槽、总上下文 8192、物理 microbatch 128；关掉 RAM prompt-cache 池以避免跨对照借用其他快照。每个提示块先保存目标的 512、1024-token 两个整槽检查点，各试空载、已有解码、已有解码且有固定同槽后继三种模式，随机配对顺序、每次清槽。4B 512-batch 连续合批开/关共用 8 个提示块，4B、16 层衍生配置在 256-batch 各有 8 个独立新提示块、目标改为 1792 tokens。该非发布模型继承同一权重前 16 层，不代表另一真实部署。每进程一份完整热身不入统计。

目标时间从**调用恢复开始**到接收首 token；后继从提交到首 token；同行记录 SSE token 间隔（ITL）与首末 token 之间的解码流时间。服务器单独回报实际缓存命中、续算 token 数和 restore handler 耗时。客户端 RPC 时间还可能包含调度等待和 HTTP；相邻片段与 RPC 时间重叠只定位现象，不把重叠量当成因果。文件为本实验刚写的检查点，**没有控制冷 SSD**。客户端严格检查请求生成长度、真实命中深度与后续工作量；不把贪心 token 一致当逐位检查点等价证明。数字都按提示块配对，重复提示不当成新流量。

## 主配对与留出

192 个正式强制动作尝试（4 条配置各 48），171 个完成，组成 **85/96 个完整配对**。85 个可比配对里，深恢复均使目标更早收到首 token；这只是本轮选定两候选和工作量内的现象，不是线上“总选更深”的规则。完整配对的目标首 token、同行与后继的可见输出一致；这不验证其他请求或数值逐位等价。

下表单位 ms，取每块的「1024 − 512」再取中位数。`同行 ITL` 指整段最长间隔。

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4B／512，连续合批开 | 8／8／8 | −202.41 | −218.10 | −51.11 | −248.52 | −58.58 | −256.08 |
| 4B／512，连续合批关 | 8／8／8 | −170.78 | −209.36 | **+10.29** | −217.84 | **+13.27** | −240.91 |
| 4B／256，独立提示留出 | 8／8／8 | −198.63 | −272.56 | +0.46 | −206.29 | −4.01 | −254.09 |
| 16 层／256，独立提示留出 | 8／2／3 | −91.67 | −217.93 | −12.51 | −95.89 | −6.15 | −152.86 |

在 4B 禁用连续合批的分线，目标收益和同行损失同时出现：已有同行时，最长间隔多出超过 10 ms 的配对是 4/8；加后继时是 5/8。后继模式的 24 个 4B 配对中有 21 对在两个臂都观察到提交后继时目标仍活跃；其他三对保留，但不当作已经确认的排队暴露。两档 4B 连续合批的整段最大间隔大多改善或持平，但仅看与恢复 RPC 交叠的间隔，中位差可能向相反方向变化。

**16 层的延迟不能作为泛化通过证据。** 正式有同行的 32 个尝试中 **21 次失败**；服务流给出 `500`、`Content-only` 格式错误。取同一八个同行提示独跑，不提交恢复或后继，16 层仍有 **5/8** 失败，4B 是 **0/8**；五个失败提示也在并发试验失败。因此恢复或竞争不是触发此错误的必要条件；还不能断定根因是权重裁剪、原始 token 压测输入还是服务器输出解析。表中 16 层有同行数据来自少数完成的配对，不能用于可用性或尾部外推。

## 恢复、续算和探针扰动

同本机 4B 512-batch 连续合批，用另一批 8 个提示块各随机运行七种条件：同行独跑、两深度各自只恢复、恢复后续算且不读探针、恢复后续算且读两个探针。它更适合回答「同行卡顿来自哪一段」和「观测器是否在改变调度」，不用于 A/B 策略收益。

- **只恢复 vs 同行独跑：** 同行最长可见间隔在浅／深恢复分别增加 **31.56 / 43.69 ms**（两者均 8/8 超过 10 ms）。深比浅单独多 **11.89 ms**。这直接说明启动真实恢复操作本身就能扰动解码流，但不等于某个 DMA 或同步阶段的时间。
- **不轮询、恢复后继续算：** 深比浅让目标首 token 提早 **243.06 ms**，同行整段最长间隔反而缩短 **54.36 ms**；深恢复消耗更多，不妨碍它凭借缩短后续 prefill 减少整段卡顿。这不是不同合批模式间的因果归因。
- **两次同步探针：** `/slots` 两次调用合计中位 **189.35 ms**；加入它们让目标首 token 再迟 **187.05–197.51 ms**（两深度分别比较）。不能把同步 HTTP 探针当免费在线特征采集，也不能将这些数字等同策略代码耗时。
- 其中一块服务器报 64 token，但全七臂只有 63 个有内容或 token ID 的 SSE 片段；用客户端可见间隔，不填造第 64 个时间戳。排除该块，深/浅的只恢复对照仍增加 **12.00 ms**，无轮询续算对照仍缩短 **52.84 ms**。

## 为什么旁路和闭环不能直接宣称通过

有些信号能取到：扩展 `/slots` 快照在 16/16 个探针动作里看见目标闲槽恢复前后的 `n_prompt_tokens` 从 0 变为实际的 512 或 1024，因此不能笼统说“恢复长度不可见”。但占满两槽再追加两个请求时，`/metrics` 的待处理数可见为 **0→1→2**，`/slots` 始终只有同两个活动任务 ID，不返回排队请求的身份、顺序和恢复候选，也不显示共享暂存中的依赖和就绪事件。不能把之后的缓存命中和完成时间回填为决策时的输入。

本机接口能强制**整槽恢复**和指定槽的运行请求，不能把一个候选的共享检查点同时放入独立 HBM 暂存、在随后消费时原子移交，也没有可由策略控制的预取准入。GPU 调度器自身的批次和同步与项目冻结恢复执行器不同。一个只在线猜 `cache_n` 的补丁会更改策略定义；所以没有做所谓「真实 `local-cost` vs `entry-replay`」接管或把强制较快动作当离线最优。要进入下一步，至少要补一个调度器内部快照及单候选执行日志，先证明快照和动作可对齐，再谈留出 A/B、SLO 非劣与跨部署。
