# GPU 系统对照：同槽提前恢复

**结论：同槽提前恢复可以把冷状态准备移到请求释放前，但未能稳定缩短目标首 token 或整组完工，本轮不推荐启用。** 即便提前知道正确前缀，按时就绪也不保证加速。

待验证的问题：只提前提交已经选定的深恢复，能否改善目标首 token 或共同完工？早期的延迟对照表明批次变化能转移等待，不能用同行响应改善替代这一目标。这里不联调边界选择。

选择可在现有引擎上执行的单槽方案：已知某请求的精确 1,152-token 前缀与对应的冷状态文件，目标槽中原有 1,024-token 浅前缀。在观测到精确前缀的提示后，可以异步对原目标槽提交恢复；完整续算输入到达后，等同一恢复完成才发起续算。两条深恢复路径都占同一个目标槽，不保留第二份设备状态；并发同行仍在原槽。提前提交可能更早覆盖浅状态或阻塞同行，均应计入。这个控制假设已提前确定并提交深边界；它不能测量预测器、取消或提示错配的成本，也没有增加运行时未来可见性。

设计：以同行提交为共同零点，完整目标请求在固定时刻释放。配对比较立即浅驻留、到达时按需深恢复、比到达早 150 / 400 ms 发起的深恢复；另用零提前量核验实际路径。当提前时间不同，保持相同的完整请求释放时刻、提示词、已有浅状态、文件冷读和服务槽数。记录恢复起止、目标合法释放时刻、是否赶在释放前完成、实际入批及首 token、同行响应、共同完工、覆盖浅状态的时间及提前持有窗口。通过一条后台提交线程完成与正常服务器相同的恢复 API，不以人工休眠替代恢复。成功判据：比按需深恢复同时改善目标和共同完工；部署候选还要与原来的浅驻留比较。不能同时改善时保留取舍和反例。

若已对同一槽发起深恢复，就不能无成本回退浅状态。后续仅在存在可重复收益时检验错误提示、取消或竞争；若优势依赖长提前量或理想提示，应明确适用边界。文件页预热可补作读盘上界，但不计为可部署的提前恢复结果。

## 首轮配置与复现

RTX 4060、Vulkan、Qwen3.5-4B Q4_K_M、llama.cpp b10923，仍使用两个推理槽。目标 2,560 token，同行 1,792 或 2,816 token，已有 512 token 驻留。目标从同行客户端提交后 550 ms 起有资格发出续算。按需恢复（提前 0 ms）和提前恢复由同一个线程池调用相同 API；线程只负责提交，服务端是否能立即处理由实际运行决定。浅驻留也使用同一释放时刻。恢复开始与响应到达之间不能直接观测槽内覆盖的瞬间；恢复完成早于释放的时长只表示确认就绪后等待释放的时间。设备并行配置相同，未将引擎内部临时拷贝的峰值等同为零。

种子 7321，每个提示词块随机交叉两种同行长度和四条路径；首块预热后保留六块。先核对浅初始缓存、冷读卷计数、实际续算 token、目标未提前提交以及首 token。分组同时报告最大释放抖动，目标时钟从预设的释放时刻计，全部抖动包含在结果内。

## 首轮实测

12 个配对块、48 条测量均通过缓存和阶段核对，块内首 token 均一致，释放观测时刻最大晚 0.79 ms。目标在全部 48 条运行中最后完成，因此本轮目标收益和共同完工收益相同。以下相对按需深恢复，正值为快：

| 同行输入 token | 深恢复提前 ms | 释放时已就绪 | 释放后等待中位数 ms：按需 → 提前 | 目标／完工收益 ms | 同行收益 ms |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,792 | 150 | 0/6 | 58.60 → 47.67 | +20.73 | +0.67 |
| 1,792 | 400 | 6/6 | 58.60 → 0.00 | +20.23 | −64.63 |
| 2,816 | 150 | 0/6 | 174.62 → 169.62 | −4.21 | +64.08 |
| 2,816 | 400 | 0/6 | 174.62 → 174.69 | +1.64 | −0.65 |

在较短同行组，提前 150 ms 相比浅驻留目标平均快 34.65 ms，5/6 配对更快；该组按需深恢复的均值受单对影响，不能据此断言所有目标都适合深恢复。提前 400 ms 虽然完全遮住恢复等待，却没有提高目标的平均收益，并使同行相比按需恢复慢 64.63 ms。较长同行组两档提前恢复相对浅驻留目标慢约 24–30 ms：即使提前 400 ms，恢复调用更早发出，服务端报告阶段中位数仍约 147–149 ms，而恢复返回亦未更早。三条深路径的目标首批间隔中位数都约 930–932 ms，支持“提前发出不保证提前就绪”；未直接细分队列等待和设备同步。

## 留出复测与决定

首轮完成后冻结两档提前量、释放时刻和候选，只换种子 7322，并取未参与首轮的 1,920 / 3,072 token 同行。10 个配对块、40 条测量，块内首 token 均一致，释放最大抖动 0.71 ms，目标仍总是最后完成。

| 同行输入 token | 深恢复提前 ms | 释放时已就绪 | 释放后等待中位数 ms：按需 → 提前 | 目标／完工收益 vs 按需 ms | 目标／完工收益 vs 浅驻留 ms | 同行收益 vs 按需 ms |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,920 | 150 | 0/5 | 76.73 → 80.55 | −24.34 | −75.14 | −0.25 |
| 1,920 | 400 | 5/5 | 76.73 → 0.00 | −22.99 | −73.79 | −59.01 |
| 3,072 | 150 | 0/5 | 412.29 → 226.25 | +10.96 | −4.41 | −269.88 |
| 3,072 | 400 | 0/5 | 412.29 → 227.64 | +3.20 | −12.17 | −337.21 |

短组提前 150 ms 在 4/5 对比按需更快，平均仍为负；4 号块比按需慢 249.44 ms，首批间隔多 228.18 ms，而服务端报告的目标续算只多 13.46 ms。分歧主要表现在目标入批前后，不能用续算增加解释。这并不证明 228 ms 都是 SSD、同步或队列中的某一项。短组提前 400 也有一对慢 239.5 ms；这些实际波动保留在均值中。

两个种子合计：400 ms 提前量在两个较短负载的 11 对中都能提前就绪，在两个较长负载的 11 对里一次也没有。**这是稳定的就绪差异，性能收益却没有跨工况保持。** 较长留出组虽减少释放后恢复等待，目标相对按需仅好 3–11 ms，同行反而慢 270–337 ms；四个留出工况均未超过浅驻留的目标和整组均值。在这条没有额外 GPU 槽的现有路径上不推进部署或错误提示／取消分支。若再研究，需先改变并独立测量恢复的服务端排队路径或引入可用的预取隔离；本实验没有验证其收益。
