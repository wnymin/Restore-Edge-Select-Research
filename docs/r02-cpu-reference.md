# R02-CPU-01：完整求值开发参照

2026-11-19，本方准备参照与核对材料，不变更协作者分工。这 24 个快照、48 个固定候选臂是**开发集，不是独立留出**。没有在本步骤引入状态简化、用时对照或策略替换。

## 如何复算

从实验仓库根目录执行：

```powershell
python -m scripts.cpu.lookahead.staging.prepare_r02_cpu_reference --check docs/evidence/r02-cpu-dev-v1.json
```

[开发参照](evidence/r02-cpu-dev-v1.json)包含构造输入、配置入口、额度（字节）、选点前快照，以及逐臂的固定后继、预留时刻、计算开始、逐对象传输和逐请求完成向量。时间用精确有理数（JSON 字符串）记录。`initial_snapshot` 是 B 首次选点处；`next_head_state` 是候选干预后 A 完成、B 进入队首处理前的切面。每个臂分别在原执行器里做了三次交叉核对：从头固定回放、从同一首选点完整求值、暂停后从 B 队首续算。第三种返回的是后缀，比较时必须前接 `completed_before_resume_ms`；调用每个分支前独立复制可变快照。完整执行和续算的完成向量在开发集内一致。

## 可用样例

| 样例 | 开发用途 |
| --- | --- |
| `distinct`、`shared-kv`、`shared-checkpoint` 各两档 SSD 成本，以及并集额度阈值 −1、0、+1 B | 对照真实共享对象并集与按请求重复计费；分别记录等号处理和快照对象身份。三种阈值分别为 178520064、140771328、89260032 B。 |
| `release-ready` 三例 | 145 MiB，B=576 臂在 30 ms 释放并使 C 重试；D 就绪处于释放前 1/4 ms、同刻、后 1/4 ms。原执行器在第三例的 B 队首切面仍有 D 搬运在途；另两例无在途。 |
| `head-demand` 和 `head-demand-exact-tie` | 额度为 0，预取不可用，但原队首按需恢复有效。平局例两臂均为 `[30,38,171/4,199/4]` ms。 |
| `all-resident-control` | 无搬运阴性对照；不能把“不搬运”误作“边界无影响”。 |

`exact_minima` 保留同一候选集合的所有最低分边界；`score_order_pick` 是按 `(完成时刻和, -边界)` 的确定性排序结果。在同一快照、同一请求集上，该和与平均响应给出相同排序。`original_fallback` 单列；如果宣称等价于带 fallback／门限的原策略，仍要另外验证原策略平局和门限，不能拿排序字段代替。

## 协作者直接接手的部分

1. 从上述切面分别比较完整状态、未来相关对象＋逐对象搬运前缀、仅汇总字节和成本。在 `release-ready` 例优先核对 D 在途身份／余量和 C 重试；在共享例核对同一个对象何时还能占额或被续算使用。
2. 冻结独立于这些开发例的输入和成本档，再测判据。需要补足共享 × 释放的直接配对及其他未覆盖的交叉、同刻工况；不要把开发集或 R01 已发表见证当留出。若出现冲突，交精简反例、两条轨迹及适用边界；若通过，保真后才测净成本。
3. 按[交接接口](r02-cross-review.md)回传选中动作、精确平局、逐请求完成向量、回退及复算命令。开发参照没有证明存在可替代完整求值的状态简化。
