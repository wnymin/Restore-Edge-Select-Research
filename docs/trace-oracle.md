# 恢复边界策略、离线最优与可降空间

**常规成本保留逐请求基线。** 受压时，若只优化均值，入口剪枝策略通常以更低的选点开销接近离线最优；若需要限制单请求退化，改用带约束的自适应搜索，并报告该约束的代价。压力倍率是模拟输入，不是硬件部署阈值。真实服务证据单独见[实测与外推](gpu-boundary-restore.md)。

## 策略

| 策略 | 选点依据 |
| --- | --- |
| `local-cost` | 最小化当前请求独占时的搬运、必要复制和后缀续算总成本；同分取更长前缀。 |
| `entry` | 在已到达队列中比较当前候选，最小化可见请求完成时间之和。回放入口用只计计算的下界剪掉无胜算的候选；其余候选照常推演，与 `next4` 的零开销结果一致。 |
| `mixed-reuse-estimate` | 搬运可能抵消复用收益，或发现已驻留、已预留和活跃 KV 可共享时，直接用队列快照估算；不回放候选。 |
| `adaptive` | 以快照排序候选，用有限推演核对均值改善和窗口内的单请求代价。筛选版可直接回退，均值版取消单请求限制。 |

## 自适应选点

在请求首次入窗时，输入仅包括已到达请求及已提交边界、可行候选对应的依赖、RAM/SSD 路径、已驻留和已预留的对象、所剩预取字节、传输积压和前方计算余量。模型需要续算和搬运成本以及当前资源进度。压力倍率和轨迹编号都不参与决策。已经开始的服务、已经提交的边界、缓存放置和候选集合不变。

| 按顺序识别的状态 | 可执行的选点方法 |
| --- | --- |
| 只有一个合法候选 | 直接选它，零推演。 |
| 队首没有同行、在途搬运、动态驻留或预留占用 | 枚举独占搬运、必要复制和续算之和，取 `local-cost`；同分选更长边界，零推演。 |
| 容量竞争 | 存在一个非零候选，所需新增额度不超过总预取预算，但当前放不下。使用队列搜索，总计最多三次推演。 |
| 共享 | 有可立即预取的候选，命中驻留、预留或当前活跃 KV。用增量成本排搜索顺序，最多三次推演。 |
| 跨层候选 | 非零候选的检查点分布在 RAM 和 SSD。由队列搜索复核变更，最多三次推演。 |
| 重叠或积压 | 有可预取候选、前方有计算，且候选增量搬运加传输积压至少抵消其省下的续算；或者已经有传输在途或积压。最多三次推演。 |
| 其余轻负载 | 搜索只允许两次推演。可选快速模式在既无容量、共享、重叠、积压信号，也无候选快照评分严格领先时直接回退；该模式允许跳过部分轻负载或跨层决策，并标记为未认证。 |

所有非平凡搜索先推演 `local-cost`，因此两次预算指基线加一个候选。后续最多纳入四个已到达请求，后续边界固定为各自的 `local-cost`；预测中的前方请求使用已提交边界。用近似快照评分排序：后缀续算与必要复制，加上前方计算预计覆盖不了的等待；放不进预取额度时，把新增搬运放到队首。排序只决定先试谁，未经推演的候选不能胜出。候选用同一事件模型回放后，只有可见请求的响应总和净改善超过每个可见请求 1 ms，且没有可见请求比同快照基线慢超过 10 ms 时，才可替换基线。本地运行可配置预算、窗口大小、增益门槛和单请求容忍值。0 ms 是严格保护，关闭上限是只优化均值；这两者是服务目标的选择，不由压力倍率自动改变。

运行时应先核实状态和成本的时效。无法获得所需状态、模型不支持该拓扑或业务未定义容忍值时，保留 `local-cost`。实现对不支持的设备拓扑和缓存留存模型显式拒绝。推演次数是确定的资源上限，Python 的决策时间以注入回放验证，次数上限不能当成真实硬件上的用时保证。

## 窗口最优性与局限

对当前候选 $c$，将时刻记为 $t$，可见未完成请求按 FIFO 排列，其剩余最低计算工作分别为 $w_1(c),w_2(c),\ldots$。对正在执行的队首使用当前剩余工作除去模型内争用倍率。逐请求完成时刻的下界是 $L_j(c)=t+\sum_{k=1}^{j}w_k(c)$。因为单槽计算不能互相覆盖，模型的搬运、同步、复制或争用都不能让计算快于独占工作，这个下界对每个候选分别成立。

令 $J(c)$ 为预测完成时刻之和，同快照中的到达时间总和是常数，所以也对应响应时间之和。若某个候选的下界已经不能达到最小收益、不能通过逐请求约束，或总下界已不可能优于当前赢家，就可以安全跳过它。达到预算时，记全部未排除但未复核候选的最小总下界为 $L_{\min}$，当前选择得分为 $J_{\mathrm{sel}}$，则：

$$
0 \le J_{\mathrm{sel}}-J^* \le J_{\mathrm{sel}}-\min(J_{\mathrm{sel}},L_{\min}).
$$

没有未复核候选时，上界为 0。$J^*$ 是同一快照、同一后续固定计划下满足收益和逐请求条件的最优得分，且始终允许基线。程序逐场景输出决策数、改选数、推演数、差距为零的次数、最大差距上界及快速筛选未认证的次数。若应用必须取得窗口内最优，可使用 `--adaptive-exhaustive`，禁用快速筛选并允许推演全部候选，仍保留可证明的剪枝。审计模式另穷举被跳过的候选，逐项检查下界，并验证差距不等式。快速模式的跳过没有这个证明，审计另报告漏掉的改选。

如果同窗口每个候选或基线的任一完成时刻预测误差绝对值可以上界为 $e$ ms，配置该上界后，把逐请求门槛收紧 $2e$，并将总收益门槛提高 $2e$ 乘以窗口内请求数。这由两种计划的误差相加得到。证书仍针对收紧后的名义模型，现实中的误差上界需要独立标定。成本高估或低估的压力实验不会自动提供这个上界。

整条在线轨迹的全局最优不可能由可见窗口证书推出。构造例中，在 70 MiB、同一缓存布局下，B 入窗时只能看到 A 和 B；只改尚未到达的 C 的到达时刻，从 2 ms 改到 29 ms，唯一离线最优的 B 边界就从 1,152 变成 576 token。任何只见相同历史的在线策略都不可能在两例里同时选中离线最优。窗口内证明、整条轨迹留出对比与真实部署是三个不同结论。

## 完整轨迹的离线基准

离线基准覆盖两批留出回放：仅 SSD 放大的 109–111 窗，以及 RAM、SSD 同时放大的 120–121 窗。每个配置固定请求顺序、检查点集合、缓存布局、预取预算、搬运规则和成本，只允许离线提前决定每个请求的恢复边界。目标是最小化到达至预填充完成的平均模拟时间。离线和在线结果均不注入选点耗时；离线最优不加入额外逐请求退化限制。

## 怎样确定最优

分支搜索每次固定下一个有多个候选的请求。回放到决策时刻后，保留实际已经发生的完成时间。从该状态向后，给未完成请求计算一个乐观下界：用独占速率处理剩余工作，免费保留已就绪对象，忽略与请求无关的未来传输、显存约束、复制与减速；仍要求 FIFO 计算槽和串行搬运，所需对象不能早于第一次可能请求它的到达时刻。对每个请求可选使该放宽模型最早完成的边界。放宽模型的每个完成时刻都不会晚于对应的真实回放，因此相加得到该分支的下界。

任何完整可行计划的响应时间都是离线最优的上界。分支下界达到或超过已知上界时可剪枝。若达到搜索上限，取未排除分支的最小下界和当前上界作为最终区间；两端相等才认证精确最优。代码以有理数计算，逐配置 CSV 以小数显示。现有 300 个三请求构造配置已用逐组合穷举核对；留出对照的基线和策略均值也逐配置核对过原始归档。

## 怎样读接近率

已有基线、算法均值分别为 $B,A$，离线最优为 $O$。接近率定义为 $100(B-A)/(B-O)$，以百分数报告。如果只知道 $O$ 落在区间 $[L,U]$ 内，用两个端点分别代入并按大小排序，得到可认证的接近率区间；若 $B=O$，分母为零，标为“无可降空间”。某档的汇总先按与原表相同的方式等权平均各配对配置的时间，再计算接近率，避免把无改善空间的配置当成 0% 或 100% 来平均。

## 后续硬件组合实验的报告口径

比较不同硬件性能组合、评估或设计按硬件环境选择恢复边界策略时，把**离线最优接近率**作为主要比较指标。每个组合分别用相同的轨迹、基线、成本和可选边界计算离线最优；不能认证精确时同时报告区间，重点看下界能保证拿到多少可降空间。接近率越高越好；95% 只是说明如何解读高接近率的例子，不设统一门槛，也不把区间上端当作保证。区间重叠时，不能仅凭下界不同断定实际排名。

同时报告基线时间、可降空间的绝对值、计入选点耗时后的净增益与单请求退化。比较有逐请求限制的策略时，注明离线目标是否也受相同约束；若不同，接近率只衡量拿到了多少无约束的均值收益，不能代替对尾部代价的判断。

[逐配置 CSV](evidence/adaptive-trace-oracle.csv) 给出策略时间、最优的上下界、是否认证精确、接近率区间与达到上界的恢复边界序列。1,080 个配置中，1,027 个有认证的离线最优解，53 个保留区间。每档结果见[汇总 CSV](evidence/adaptive-trace-oracle-summary.csv)。

正数表示快于 `local-cost`。均值与 P95 栏分别先在每个配置内统计，再对配置等权平均；请求实例计数则跨配置加总。105–107 窗在 11、12、16 倍有 14、36、36 个配置的均值改善，均为 SSD 放置。共享估计在零开销下保留了主对照全量推演约 67%–85% 的平均收益，没有候选推演；跨层回退没有改变两组 SSD 单路径对照的结果。两条路径一起受压时，共享估计仍在 11 倍首次出现收益，但该档有 22 / 7,488 个请求慢超过 10 ms（零开销），因此即使同一倍率也不能保证尾部安全。计时是本机 Python 决策耗时注入，亚毫秒差异不作为加速证据；复测的 GPU 服务与部分 CPU 回放曾并行。

结束 GPU 实验后，[单独重跑计时对照](evidence/local-cost-timing-recheck.csv)。不计决策开销的逐配置结果完全一致；11、12、16 倍的计时均值收益与上表相差不到 0.01 ms。12 倍计时下，慢超过 10 ms 的实例从 7 个变为 5 个，说明临界计数会随计时抖动；16 倍仍有 39 个。

一个[首次改选对照](evidence/local-cost-witness-11.json)解释了突变。Trace A 第 107 窗中，请求 263 的 512-token 候选可省约 168.70 ms 续算，11 倍时仅 SSD 搬运就要 169.32 ms，`local-cost` 因而重算。但它入窗时可预取，队列快照预计搬运可被此前的工作覆盖，只改这个边界就让该窗口平均响应快 150.39 ms，同时让一个更早的请求慢 9.14 ms。[10 倍对照](evidence/local-cost-witness-10.json)没有改选。这说明收益来自独占成本排序和真实队列重叠之间的差异；识别可共享状态还能保住更多改选，在该 11 倍案例中，共享估计把旧直接估计的平均收益从 289.56 ms 提到 446.06 ms。

## 机制对照

- **共享和容量会改变候选排序。** [160 MiB 手算](phase1.md#手算验收两个请求争用预取额度)中，一长一短能同时预取，两长不能。共享估计的[跨层反例](evidence/cpu-reuse-tail-witness-89.json)中，仅改一点使均值快 1.78 ms、P95 慢 9.03 ms；关闭 SSD 对计算的减速后，P95 改为快 0.72 ms。
- **估计错误会选错边界。** [同层反例](evidence/cpu-reuse-stale-witness-96.json)中，估高 SSD 耗时导致将可按需恢复的深边界改成浅边界，单步干预使窗口均值慢 361.03 ms。[共享反例](evidence/cpu-estimate-witness-77.json)显示，忽略已预留的 65.125 MiB 会漏掉无需新增搬运的候选。
- **缓存拓扑和调度可能改变结论。** [容量释放对照](evidence/boundary-reservation-placement.csv)、[双槽归因](evidence/boundary-batch-attribution.json)和[传输通道对照](evidence/boundary-lane-objective-24.csv)属于不同模型，不能把单槽窗口证书套过去。
