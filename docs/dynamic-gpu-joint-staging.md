# 多对象恢复：先算共同占用，再算延迟是否暴露

**两两能共存，不能保证一起预取也可行；一起预取受阻，也不能直接推出应该选浅。** 这一轮在项目模拟器和 CUDA 夹具中分别检验了这两步。GPU 对照里只改变后继能否和目标同时暂存、后继能否复用已搬运对象，以及释放后的计算窗口，目标自身始终快约 2 ms，整体却在紧额度和短窗口下偏好浅。

## 容量和关键路径的判据

同一时刻，一个池里已计费的对象为 $U$，新一批请求需同时预留的对象集合为 $X$。若只读对象按标识去重、容量按单对象字节记账，则新增占用是 $B(X \setminus U)$，其中 $B$ 对对象字节求和。判定式是 $B(U)+B(X \setminus U)$ 不超过额度。相同内容但独立记账的对象、写时复制、其他池的对象不能直接从这项里扣掉。这个判据只说明一批预留能否同时成立；分批进入、释放、按需加载需沿事件序列另算。只看目标逐一与同行的占用，会漏掉多个同行的合计约束；直接将每请求的总字节相加，又会重复计算共享对象。

固定依赖图时，可以精确地传递搬运延迟。把传输串行顺序、固定计算顺序及对象消费写成有向无环图，边 $u \to v$ 的最小时距为 $w_{uv}$；基准时刻为 $t_v$，边的余量为 $s_{uv}=t_v-t_u-w_{uv}$。当相同图的候选改变上游时刻及边时距时，传播到内部节点的时刻差满足：

$$
\delta _v=\max_{u \to v}(\delta _u+\Delta w_{uv}-s_{uv})。
$$

式子由两条轨迹分别取最早可执行时刻、再减去 $t_v$ 得出。所有固定到达约束都视作带绝对时刻的根节点。可以按拓扑顺序计算：平行依赖在汇合处取最晚就绪者，不把同时发生的等待相加；串行依赖可以逐段累积。如果只知道输入时刻和边耗时的上界，把它们取上界后传播，得到固定图内的完成时刻上界。若改选改变了准入顺序、去重的边、传输队列或共享对象的释放，**旧图的余量就不再是安全证书**；需先判断能否沿用同一图，否则至少重算受影响的事件。

## 项目模拟器：独立对象与共享对象

复用前一轮的精确检查点和交接释放规则。B 目标的浅／深边界为 768／1,152；C 和 D 固定从各自的 1,152 检查点恢复，分别在 2、3 ms 到达。合成 SSD 耗时取手算的三倍。只变是否加入两个同行、两个同行是否共用只读 KV（检查点独立）或提高暂存额度。B 选深始终让自身快 $26/9$ ms。

| 同行 | 额度 MiB | 选深时三者的暂存需求并集 MiB | B 选深对响应和的改善 |
| --- | ---: | ---: | ---: |
| 单独 C 或单独 D | 244 | 170.25 | 各 +5.78 ms |
| C、D 对象独立 | 244 | 255.375 | −1.89 ms |
| C、D 只读 KV 共享 | 244 | 219.375 | +6.67 ms |
| C、D 对象独立 | 256 | 255.375 | +5.11 ms |

第二行的 D 并非候选不可用，而是无法提前预留，最后按需加载。共享组相对独立组少记一次 36 MiB 的 KV，既改变准入也减少搬运；这里只归因到**对象共享的合并效果**。这是固定后继边界的干预，不是全序列最优比较。复现：`python -m scripts.cpu.replay.study_boundary_joint_phase1`。

为检验后继自行换边界能否消除这类反例，另用 32 token KV 块，让 B 可选重算／896／1,152，C 和 D 各可选重算／1,120／1,152。248 MiB 能容纳 B 浅加两个同行的深候选（247.375 MiB），却容不下 B 深加两个同行的浅候选（253.375 MiB）。枚举所有 27 种组合、对每个 B 动作都给同行最优边界：仅有任一同行时，B 选深均改善 3.90 ms；两者独立且都在时，B 选深反而增加 0.54 ms。B 选深时最好的补救是让一个后继重算，仍不及 B 选浅且两个后继都选深。保持额度但共享 KV，或保持独立对象但把额度升至 256 MiB，唯一全局最优又都变为三者选深。**即使后继也可换边界，逐对检查仍可能低估联合代价。** 这个幅度是合成例的存在性结果，不用于估计实际收益。

## GPU：受阻还要看是否错过消费窗口

RTX 4060 Laptop 上用固定 128 MiB 物理分配。目标 RAM \to HBM 浅／深搬 16／48 MiB，C 从 RAM 搬 32 MiB，D 从 SSD 无缓冲读到 RAM 再搬 32 MiB；别名对照让 D 直接消费 C 的同一份已搬运缓冲。独立组里每个同行都能和深目标占满 80 MiB，两者同时加入则要 112 MiB。紧额度下独立组的深路径等 GPU 记录目标交接后才开始 D 的 SSD 读取。目标、C、D 的合成续算在同一设备流顺序执行，C／D 分别为 2／1 ms。浅／深的目标续算分别是 7／5 ms 或 30／28 ms。改变后一对时，目标省下的续算仍为 2 ms；之前占用计算的独立窗口在三批分别为 36、32、34 ms。配对顺序随机，每轮检查实际搬运缓冲区的字节。

下表为 34 ms 窗口、未参与校准的 12 对复测；时间差为深减浅。指标是同一设备起点到各任务完成的时刻之和，非端到端 TTFT。逻辑额度由固定协议控制，它不是测得的系统剩余显存。复用是夹具中的缓冲去重，不是对真实模型缓存语义的新验证。

| 同行 | 额度 | 浅续算 | 目标差中位数 | D 差中位数 | 完成时刻和差中位数 | 深胜出 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 仅 C | 80 MiB | 7 ms | −2.00 ms | — | −4.01 ms | 12/12 |
| 仅 D | 80 MiB | 7 ms | −2.00 ms | −2.00 ms | −4.00 ms | 12/12 |
| 独立 C、D | 80 MiB | 7 ms | −2.00 ms | +5.80 ms | **+1.82 ms** | 0/12 |
| 别名 C、D | 80 MiB | 7 ms | −2.00 ms | −2.00 ms | −6.01 ms | 12/12 |
| 独立 C、D | 112 MiB | 7 ms | −2.00 ms | −2.00 ms | −6.01 ms | 12/12 |
| 独立 C、D | 80 MiB | 30 ms | −2.00 ms | −2.00 ms | −6.00 ms | 12/12 |

紧额度的独立组里，深路径下 D 的准入等待在短／长工况均约 34 ms。只有短工况会改变最优边界：长工况有足够的目标和 C 续算覆盖等待后的搬运。按该夹具的名义续算，深路径先给 B、C、D 各腾出 2 ms；短工况中 D 的搬运在交接后超过 7 ms 才开始侵入这点收益，超过 13 ms 才使响应和排序翻转。长工况同理，翻转阈值是 36 ms。

## 可用信息与留出结果

首轮只用独占 D 的 SSD 读取与上传中位数 12.574 ms 估算就绪。该规则在 32 ms 留出中未预测短工况翻转，和两两容量基线一样错 7/48 对；只要并集超额度就选浅的规则错 9/48 对。拆开看，计算窗口判据没有错，错的是把独占成本当成了等释放后的有效就绪延迟。后者还含启动、执行期成本及读盘和设备流间隙，不能直接解释为固定的带宽差。

针对该错误，用原 36 ms 校准批次中两个受阻工况的「交接至 D 就绪」中位数 14.737 ms，替换受阻路径的启动后估计；其他路径仍用独占值，未使用 32 ms 留出做参数校准。在随后独立采集的 34 ms 批次，该规则 72/72 与配对较优边界一致；两两容量、只看并集是否超限、沿用独占代价三条基线各错 12/72。这个结果仅覆盖同一设备、协议和人为配置，更新规则需要事先知道预计的配置及释放条件。没有用留出的实际就绪事件做选择，也不能把 72/72 当成生产请求的逐项保证。
