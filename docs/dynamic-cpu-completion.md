# B 组 CPU 任务结项记录

**状态：已完成验收（2026-11-18）**

本记录对应[双人研究分工](work-plan.md)中的 B1–B3，不代表整个项目完成，也不替代 A 组的 GPU 验证。

## 已完成内容

- **B1：动态状态机制。** 完成配对干预、翻转与无翻转案例、公开轨迹匹配，并记录可见队列、剩余额度、对象就绪／在途、共享关系以及目标和后续请求的完成时间变化。
- **B2：在线策略。** 完成只使用决策时可见信息的动态门控、静态特征消融和硬件分档对照；参数在校准集选择并在留出集冻结。`entry-replay` 直接复用已确定边界，保持 `entry-fast` 的零开销选择和执行结果。
- **B3：留出验收。** 完成 480 个留出配置的共同输入对照，报告零开销平均响应、选点时间、含开销净收益、P95、单请求损失和离线最优接近率；未认证精确最优的配置报告区间。
- **复现与审计。** PR #4 已合入主分支（合并提交 `106c0ce`），提供无需 GPU 或原始轨迹下载的 CPU 验收入口，并修复到达时间数值／字符串混用时的排序问题。

## 已确认结论

1. 动态容量、共享、队列和到达状态能够改变同一恢复边界的收益。
2. 动态门控可以减少推演次数，但计入本机选点开销后，尚无证据证明它稳定优于简单 `entry` 基线。
3. `entry-replay` 降低的是已确定边界的推演成本，不改变策略选择；其本机计时收益不能直接外推为真实服务端到端提速。
4. 离线最优在部分高压力配置上仍只有区间，不能把未收敛区间写成精确最优。
5. 首次入窗立即提交且未来请求尚不可见时，存在在线决策损失；更准确的当前状态估计不能消除这类未来信息限制。
