# 恢复边界研究约束与无上下文接手指南

本文整合项目中已确定的范围、模拟语义、证据口径、动态因素取舍和当前交接状态。新 agent 先读本文，再按任务查阅 `docs/simulator-baseline.md`、`docs/trace-oracle.md`、`docs/experiment-index.md`、`docs/dynamic-gpu-lookahead-report.md` 和 `docs/dynamic-cpu-completion.md`。报告保存具体参数、证据和推导；本文保存跨任务约束。历史计划不能覆盖已验收状态。

## 研究范围与固定语义

- 研究给定缓存放置、合法检查点和固定执行规则下的**恢复边界选择**。不把任务默认为 FIFO/LRU 淘汰、活动 KV 分配、近似恢复或服务调度器重写；工程修复不是研究贡献。
- 基础模拟以 Qwen3.5-4B、CPU 元数据事件模拟为主，沿用精确检查点恢复：非零边界需要完整前缀 KV、边界循环状态及卷积历史，`0` 从头重算。固定请求顺序、单计算槽、串行传输、共享预取额度、首次入窗选一次；预取失败不等于候选不可执行，队首仍可按需加载。
- 预留即计费，共享按对象身份去重，在途搬运、交接、释放和同刻优先级按原执行器处理。放宽到达、通道、驻留、带宽或批处理等假设时，一次只放宽一个，先写明原结论失效位置，再重跑最小反例、边界和留出验证。
- 常规成本保留逐请求 `local-cost`／`entry` 基线。R07 以冻结的 `entry-replay` 为主干，检验原策略在放宽负载假设后的适用范围。动态门控可使用决策时已可见的队列、额度、共享、就绪／在途和可覆盖工作；静态策略主要依赖成本、布局、硬件档位等配置。`entry-replay` 是固定边界推演优化，不是新选择策略。

## 放宽假设的研究顺序

后续研究默认按以下顺序推进：

1. **模型与成本域。** 保留恢复和执行语义，改变 KV／检查点字节量以及续算、RAM／SSD 搬运成本，检验门控能否迁移。[R06 模型与成本适用域验证](archive/r06-process/r06-model-cost-transfer-plan.md)承接此步。
2. **到达与队列状态。** 固定模型成本及资源语义，依次改变到达强度、突发程度、可见队列长度和前缀共享程度，判断哪些在线状态是必要的。[R07 `entry-replay` 泛化性研究](r07-entry-replay-generalization.md)先承接到达条件；共享程度作为条件扩展。
3. **并行资源与执行语义。** 先只增加一个传输通道，定位旧规则失效的事件关系；再分别考虑多计算槽、批处理或动态带宽。
4. **GPU 与服务验证。** 测量恢复、搬运、续算和决策开销，校准模拟成本；再独立检验真实服务的 TTFT、TPOT、尾延迟与吞吐，不以模拟计时代替实测。

每一步先冻结上一阶段的实现、证据和对照。使用同输入的单因素配对实验，以最小反例和临界状态定位失效条件；只在校准集调整规则，再用独立留出验证。单因素检验后才测试组合。若更改顺序，在阶段台账登记原因和影响；没有净收益或超出预设损失预算的工况保留回退，不外推有效域。

## 动态因素优先级

后续研究按 R03 结项标记安排投入。早期配对证据和升降级条件仍可供复核。[R03 因素结果序列](r03-factor-sequence.md) · [动态因素评估与优先级](dynamic-factor-priority.md)

把**影响程度**和**量化／评估难度**分开登记，不因难测就默认低影响。优先顺序如下：

1. 影响大且容易量化：优先做配对实验、留出验证并进入策略候选。
2. 疑似影响大但难测或只能事后观测：先做辨别实验、代理观测或上下界分析；证据不足时保留区间、完整推演或回退，不直接忽略。
3. 影响较小且容易量化：做低成本消融；确认遗漏损失在预算内后可简化。
4. 影响较小或未知且量化代价高：暂缓建模并登记证据缺口；只有损失验收通过才能称为可控忽略。

优先候选通常包括：对象并集／剩余额度、对象就绪与在途、已到达同行的剩余计算及可覆盖搬运量、共享身份、传输队列和释放时机。它们不是预设排名，必须由配对证据确认。区分**可行性／信息约束所需状态**和**只用于收益预测的特征**；前者不能用平均损失预算豁免。未来到达、事后完成时间和离线标签不可作为在线特征。

每个因素至少记录：机制、决策时可见性、单位、采集和决策开销、证据范围、是否导致动作翻转、忽略损失、适用域和回退动作。

## 忽略因素的验收

- 先声明目标、参照、适用工况和损失预算；本项目不设统一阈值，未指定时用校准数据做敏感性分析，不能把临时观察值当成门槛。
- 用相同输入、快照、成本和执行器做保留／省略因素的消融。先做固定其余边界的单次干预，再做闭环留出，分别记录平均响应、决策耗时、净收益、P95、单请求退化、翻转率和机制指标。低翻转率不等于低损失。
- 覆盖正常点、容量临界、事件同刻及单侧邻域、共享／在途交接、候选近似平局和因素组合。单因素损失小不证明联合损失小；仅检查四角不证明全域安全。
- 若精确最优未认证，报告区间和下界；若省略因素的损失超预算、区间跨预算或证据不足，则保留因素、缩小范围或回退基线。多步保证必须相对一致的延续参照逐次认证，不能直接累加相对旧计划的单次结论。

## 证据与交接

- 并行分工从固定的共同版本开始。每位负责人应能独立完成前置、自验和最终交付，必要时各自复制样例或复跑基线。共享索引和跨线复算交给阶段末的汇总人。若一项任务必须使用另一线新产出的结果，把它列为汇总任务或下一阶段任务。

- 区分模型内证明、CPU 模拟、GPU 实测和外推。模拟压力倍率不是硬件阈值；CPU 决策计时不是 TTFT、TPOT、吞吐或 SLO 实测；减少模拟事件不等于净在线加速。
- 公开轨迹的校准／留出按窗口、种子和成本工况冻结；构造例只证明可能性，不估计生产频率；同一轨迹的多组干预不是独立生产样本。报告必须保留失败案例和适用边界。
- 从仓库根目录验证：`python scripts/check_fixture.py`；CPU 交付可运行 `python -m scripts.validation.check_dynamic_cpu_delivery`（若当前提交包含该入口）。代码、配置、脚本和精简证据分别放 `src/`、`configs/`、`scripts/`、`docs/evidence/`，原始轨迹、模型权重和机器专用文件不提交。

B1–B3 CPU 分工已验收，不要当作未完成任务。当前未决重点是一般多请求的必要状态、真实状态误差覆盖、多步可组合保证、证书构造的净开销，以及与 A 组 GPU 机制证据的交叉验证。CPU 结项不代表 A 组或整个项目结项。
