# R09：选点时间、质量与预算实证

**2026-11-25｜结项。主建议：默认保留 `entry-replay`，预设 0 ms 额外搜索；本轮不启用正预算。** 本文回答 CPU 选点时间能否与已有工作重叠，以及多做推演能否改善恢复边界。默认策略仍是 `entry-replay`。实验在 R08 的精确恢复、固定放置、单 GPU 计算槽、单串行搬运和串行选点执行语义下进行。实测成本回填不是线上服务实测。[计划与锁定规则](r09-decision-time-budget-plan.md)

## 先区分三种时间

- **CPU 选点耗时**：在本机用 `perf_counter_ns` 测原策略或候选的决策回路；原策略本来也耗时。0 ms **额外搜索**不是要求 CPU 瞬间完成。
- **事件保守余量**：在动作固定的配对回放中，发布可延后到什么程度，既不推迟任何原预留或搬运发出，也不增加 GPU 等待。**性能余量**允许搬运晚，但每条请求的 GPU 开始和完成均不晚、峰值暂存不增加。两个量分别统计。
- **净响应**：计入实际决策耗时后允许动作变，按原队列与搬运语义闭环。它既不等于“零开销收益减去 CPU 用时”，也不能从固定动作余量直接推出。

测余量时，每个基线样本先冻结动作与逐请求 CPU 耗时，再回放同一份耗时和动作，独立改变发布时间。0 延迟必须逐请求匹配选点、预留、搬运始末、GPU 开始与完成。决策等待期间，在途计算和搬运可继续，新预留、搬运发出和后续选点由原串行执行器等本次发布。微用例验证了：同一块 640 ms 空档可以分别掩盖两次单独延迟，却**不能同时**掩盖两次 640 ms 延迟；另有 GPU 忙但预留立即被推迟、GPU 空闲的 0.05 ms 延迟直接影响完成的对照。

## 校准：空档存在，但“GPU 正忙”不是安全预算规则

在 [104 个校准配置](evidence/r09-inputs.json)中，实测成本回填 4B 主域有 6 个源窗、24 个配置。主规则用**实际决策开始时**已知的 GPU 忙闲，只给 GPU 正忙且有多条合法边界的请求追加同一上限。该规则启用了 330 次决策，但从 0.05 ms 开始所有被扫描的正档都导致 **6/6 个校准源窗**至少一项性能退化，故 [预算锁](evidence/r09-budget-lock.json)在新窗运行前选定 **0 ms 额外搜索**。

单次延迟不是整窗规则：主域校准中，260 个 GPU 忙且冷数据当下可争取发出的多候选决策，事件保守余量的已测前缀都是 0；其中 243 个却在单独延后 32 ms 时仍不损失计算开始或完成。这意味着错过一部分提前发出机会不必然导致请求变慢，也意味着不能用 GPU 忙剩余时间统一设预算。32 ms 是主网格最后一档，不是余量精确值。

同一零开销快照的阶段比较也复现了已知区别：同视野复核在 104 个校准配置均未改选；扩大到更多已到达请求在 B481 补回 **13.251 ms**；允许后继联动在 B482 补回 **252.670 ms**。B470 的同视野收益仍被尾部守门拦下，关守门的诊断对照可补回 **4.733 ms**，不具备部署资格。这些是**动作质量**的数据，不能当成限时策略的净收益。

## 同窗分配预算：0.05 ms 也不能按 GPU 忙闲统一放行

对主域每个新窗的四个配置，按**决策发生时**的忙闲状态同时施加额外延迟，而不是给每个请求事后按各自的单次余量分配。主档 0 ms 相对基线无退化。0.05 ms 补验给 1,207 个符合规则的决策加时，**12/18 个源窗、32/72 个配置**出现至少一个 GPU 开始或请求完成变晚，最坏延后约 **0.183 ms**。0.25、2、8 ms 同一规则下均有 **12/18** 个失败窗；四个正档的事件保守条件均在 **18/18** 个窗出现违例。这里的失败是严格的「不增加等待」判据，不等于这些差值都达到 +1 ms 的候选验收线。[固定动作预算曲线](evidence/r09-fixed-action-budget.csv)

追加的 [104 个临界点诊断](evidence/r09-critical-points.json) 细化了 75 个配置里的低余量和右删失实例，并保留预留／搬运明细。B481 的索引 7 与 B482 的索引 16 虽仍有约 **82.30／292.87 ms** 的模拟 GPU 活动，固定动作仅延后 **0.0125 ms** 已触及性能失败；这是已测上侧点，不是准确截止时刻。与之相反，诊断子集有个别固定动作决策通过至 **512 ms**。二者都不代表出现频率。主域 24 个校准配置另用六份基线实测计时重复注入，0.05 ms 的判定为 **11 点六轮均失败、13 点六轮均通过、0 点翻转**；六次计时没改变本例的方向。[锚定计时敏感性](evidence/r09-anchor-sensitivity.json)

**统计判定：** 18 个非重叠源窗来自 3 条原始流，不能视为 18 个独立部署或相互独立抽样。哪怕假设 18 窗独立且零失败，单侧 95% 精确二项上限也约 **15.33%**，仍高于 5% 门槛；在单一冻结规则零失败时至少需 59 个独立单位。实际正档已在描述性留出上违反门槛。故只推荐 **0 ms 额外搜索**，不发放 GPU 忙、容量受阻或其它细分子域的正预算。0 ms 是维持原路径的回退选择，不是证明不存在任何正余量，也不是独立流量置信声明。

## 时间—质量与预算—净响应的两条曲线

时间—质量的四个点均从同一序列的零开销冻结快照选动作。CPU 时间是每配置所有候选钩子的额外时间和，再取配置中位数；没有模拟为串行响应阻塞。留出 288 点中 **287 点**得到精确离线最优，**285 点**的冻结基线为已认证最优或近最优。

| 同视野复核 | 1.527 | 0／104 | 0.987 | 0／288 |

改选率和收益并不随多算的时间普遍上升。唯一有留出动作收益的点是 Trace B 窗 161、27B 架构代理、16×、384 MiB：后继联动补回精确缺口 **71.876 ms**，不限时策略六轮配对的含开销均值还改善 **65.982 ms**；8 ms 档没有在时限内改选，均值反而多 **7.537 ms**。校准回归里，B481 的 8 ms 档仍能省 **13.811 ms**；B482 只有不限时臂在该次校准保住大收益（含开销约 **213.064 ms**），8 ms 档慢 **25.400 ms**。这证明有值得算的个例，但不能用它们给所有窗口分配预算。[分阶段曲线与按域数据](evidence/r09-search-time-quality.csv)

## GPU 可观测性

本机归档的 `/slots`／HTTP 同时探测可见请求是否处理、HTTP 恢复区间与 token 输出轨迹，但没有处于同一执行时钟的**选点资格、对象级预取发出、GPU 计算边界**。按现有 8 个配对块复算，两种恢复深度下探针调用区间总和的中位数分别约 **189.84 / 178.79 ms**，探针臂的目标 HTTP 响应中位数相对无探针配对分别 **+197.51 / +187.05 ms**。因此不把 HTTP 时刻作为事件级预算，不追加不可对齐的真机 A/B。[GPU 可观测性复算](evidence/r09-gpu-observability.json)

## 结论与复核入口

1. **有可隐藏的选点时间，但没有证据支持统一的非零默认预算。** 在这套串行发布路径，GPU 前驱仍在执行不保证可以推迟下一次预取；已有在途搬运和单次空档也不能按请求重复分配。未来若要验证某一正预算，至少要能在选点时识别最近会受影响的发出／接管事件，并验证组合消耗与实际准时发布。
2. **动作收益存在，限时后未在新留出带来可接受的净收益。** 保留默认策略；到期提交冻结动作，不让部分回放结果覆盖原动作。当前软限时仅供实验，若将来需硬保证，须先解决推演步不可中断与发布时间问题。本轮不改默认执行器，不声称真实 GPU 服务收益，也不否定更便宜的判定或真正独立发布机制的可能性。
