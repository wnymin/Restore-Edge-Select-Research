# 逻辑批量会改变同槽恢复的执行时机吗？

[上轮](dynamic-gpu-restore-queue.md)关闭空闲槽保存和自动检查点后，长负载恢复仍排队；两个相邻短负载的提前恢复收益却翻转。本轮比较逻辑批量上限 2,048 和 1,024，物理微批量固定为 512。两种配置都关闭上述两项缓存操作，仍使用同一 RTX 4060、Vulkan、Qwen3.5-4B Q4_K_M、两个槽和提前恢复的显式检查点。固定种子 7325、1,856 / 2,048 / 3,200 token 同行长度、550 ms 目标释放时刻，按原顺序重复浅驻留、按需深恢复、提前 150 / 400 ms 四条路径。每个配置先跑一个预热块，再保留四块。此次先启动较小批量，再启动新的 2,048 对照；原留出可用于核对基线是否漂移。

主对照看提前 400 ms：恢复任务是否更早进入最后一次分派、恢复是否也更早完成、目标与同行有无收益。所有服务端阶段只用同一日志时钟相减。最后一次恢复分派相对同行收件、同行释放分别报告；前者说明实际执行时机，后者检验恢复是否能在同行仍活跃时执行。另在每个批量配置内和同块浅驻留比较，避免把配置自身的影响当作边界选择收益。两项响应和由目标释放至首 token 和同行提交至首 token 相加；共同完工从同行提交计。

## 结果

两档各 48 条有效测量，启动日志确认实际逻辑和物理批量，48 个跨档匹配均返回相同的目标首 token。提前 400 ms 的 12 个跨档配对中，缩小逻辑批量让成功分派全部提前，并把释放前就绪从 **1/12** 提高到 **12/12**。

| 同行输入 token | 恢复排队中位数 ms（2,048 → 1,024） | 恢复回调中位数 ms（2,048 → 1,024） | 释放前已就绪（2,048 → 1,024） | 缩小逻辑批量的目标 / 同行 / 响应和收益 ms |
| ---: | ---: | ---: | ---: | ---: |
| 1,856 | 345.18 → 29.69 | 54.69 → 224.76 | 1/4 → 4/4 | +13.60 / −44.44 / −30.84 |
| 2,048 | 412.14 → 35.62 | 55.45 → 224.99 | 0/4 → 4/4 | +11.87 / −51.77 / −39.90 |
| 3,200 | 377.79 → 24.89 | 229.13 → 224.63 | 0/4 → 4/4 | +20.66 / −114.08 / −93.42 |

收益是配对均值，正值为快；目标总是最后完成，其收益等于共同完工收益。缩小批量后，12 条提前 400 ms 的恢复都在同行下一个服务端位置更新（512 → 1,536 token）之前执行。位置日志是服务端批处理标记，不能当成 GPU 完成进度。两个较短工况原先都在同行槽释放后才分派，缩小批量后都变成同行仍活跃时分派；回调增加的约 170 ms 几乎都出现在读到缓存元数据之前。长工况的恢复在两档都于同行槽释放前分派，回调时间相近，只是 1,024 档更早执行；这也解释了为什么同样减少服务端排队，回调上的影响不同。精确的设备等待与复制时段仍未分开。

3,200 token 工况中，缩小批量让目标首批相对同行首批提早约 436 ms（配对中位数），但目标首批至槽释放增加约 412 ms。2,048 档的目标首批基本和同行释放接续，1,024 档目标首批至同行释放的间隔中位数为 546 ms。目标首批更早，但与仍在运行的同行有了更长的时间重叠；目前无法把同行损失完全归给恢复回调或目标提前入批中的任何一项。

在 **同为 1,024 档** 时，提前 400 ms 对浅驻留的目标收益为 +31.77 / −20.95 / +7.16 ms，而三个工况的响应和分别变差 10.43 / 82.03 / 159.08 ms。相反，1,856 token 的提前 150 ms 在两个批量档和旧留出中，相对浅驻留均在 4/4 对改善目标，服务端实际在同行释放后才分派；该工况的收益与等待结束后及时执行一致。2,048 token 相邻工况未复现，不能把该现象当成通用上线规则。

这两个批量档分别启动，顺序未随机化；旧 2,048 档中 3,200 token 浅驻留有一次同行特别慢，本轮 2,048 档未见同等幅度，所以不把旧样本的端到端均值混入跨档估计。缩小批量确实改变了执行窗口，但单凭就绪率选择批量或边界会忽略同行损失。后续[固定深边界的四路配对](dynamic-gpu-factorial.md)区分了恢复的直接影响和恢复改变批次后的额外延迟。
