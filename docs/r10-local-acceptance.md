## R10-GPU-04 主实验判定（2026-11-26，JST）

在本机 RTX 4060 Laptop、Qwen3.5-4B Q4_K_M、82.25 MiB 逻辑暂存、单计算槽 FIFO 的预填充配置下，12 个块各完成五次配对，两策略各完成 4,800 次请求。统计核验检查了冻结配置、配对身份、回执哈希和设备事件；动作复算另将全部 120 臂的目录封条与准备归档核对。原始归档的 SHA-256 与正式汇总一致，674 个文件的 ZIP 校验均通过。[逐块、逐源及逐臂汇总](evidence/r10-native-primary-holdout-summary.json) · [运行归档](evidence/r10-native-primary-holdout.zip) · [同快照复算](evidence/r10-native-primary-action-explanation.json)

| 预登记判据 | 实测 | 判定 |
| --- | --- | --- |
| 均值改善严格大于 144.65 ms | `local-cost` 1,619.10 ms，`entry-replay` 1,609.01 ms；改善 10.09 ms（0.62%） | 未达 |
| 两类负载的均值改善都为正 | OASST +14.66 ms，百炼 +5.52 ms | 达到 |
| P95 退化小于 171.48 ms | 3,429.51 → 3,435.89 ms，退化 6.38 ms | 达到 |
| 多等超过 1,884 ms 的请求比例不高于 5% | 0%；样本内最坏单请求多等 984.82 ms | 达到 |
| 失败比例不增加 | 两策略均为 0/4,800 | 达到 |

均值与 P95 先在各臂计算，再对同块的五轮及 12 个块等权汇总。按源看，TraceA、OASST、TraceB 分别改善 85.22、14.66、12.54 ms，coding、thinking 分别退化 48.47、52.91 ms。逐块平均改善范围为 −97.48 到 +177.60 ms；去掉 TraceA 后，剩余块平均反向 4.94 ms。这些是描述性结果，同源块与重复轮次不能视为独立样本。

两条实际运行路径对同一请求的 **4,800 次配对选点全部一致**。把两策略分别放到实际记录的 **9,600 个同一快照**上复算，同样没有分歧；其中 2,910 个快照有非零候选，1,420 个有两个或以上非零候选。快照构造后，`local-cost` 与 `entry-replay` 的选择器平均耗时分别为 0.282 ms 与 0.222 ms。观测到的 10.09 ms 平均差没有对应的恢复边界变化，无法归因为选点优势。

[全量机器状态复核](evidence/r10-native-primary-environment-final.json)在 120 臂的前后快照中未观察到电池供电，配对内供电、电源计划和 GPU 标识均无观测变动；臂前温度为 41–80 °C，最大配对启动温差为 27 °C。快照不足以解释计时区间的温度、频率或耗时变化；所有 60 对均保留。服务端 TTFT、TPOT 与 SLO 吞吐见[独立服务留出](r10-native-service.md)。

[补充诊断锚点](r10-native-cost.md#预填充诊断锚点复算)覆盖三档容量、较空闲和积压工况，480 个归档的原生快照上同样未见改选；容量扫描一项仅观察到按需搬运。后来的五对原生补测确实在两个 144 MiB 工况中用到 98.25 MiB 暂存，仍未触发两策略改选。这些诊断独立于主留出判定。

[独立归档复算回执](evidence/r10-native-primary-reproduction-receipt.json)：只用冻结输入包、正式运行归档和目录准备归档重建 60 对统计，结果逐项吻合；动作解释文件与正式交付的 SHA-256 相同。复算未调用模型或 GPU，也未读取原运行目录。

[自然负载诊断](r10-natural-workload.md#用-r10-快照检验改选条件)复算两类留出有合法候选的 4,124 个快照。最深边界按冻结串行成本至少领先 244.75 ms，逐候选推演也没有发现被筛选或剪枝掩盖的改选。队列状态在假设的更高 SSD 相对成本下可以触发分歧。

[R10-ANA-01 自然负载与理论解释](r10-natural-workload.md)用四份百炼源的到达和精确前缀分布、R10 运行快照及逐候选推演解释选点一致。浅边界节省的窗口等待最多抵消 29.67%（预填充）及 27.12%（服务）的额外续算代价。

本机证据支持保留 `entry-replay` 作为当前参照实现，不能宣称它在服务上胜过 `local-cost`。如果继续研究选点，应先找到真实两策略确实给出不同边界、且不同代价能被观测的工况，再比较端到端指标。固定三请求夹具已在 250 ms 受控等待下验证改选，可作为构造对照的参照。[在线 FIFO 受控改选](r10-stage-pool.md#r10-fifo-qualification)

### 与历史实现的关系

原版 `entry` 是实现参照。[历史 CPU 对照](archive/cpu-studies/dynamic-cpu-entry.md)在已测单通道配置中核对了 `entry` 与 `entry-fast` 的逐请求选点；[后续实现对照](archive/cpu-studies/dynamic-cpu-entry-replay.md)中，`entry-replay` 在 144 个校准和 480 个留出配置中的零开销结果与 `entry-fast` 一致，留出 Python 选点时间另降 7.26%。[R10 快照桥接](r10-stage-pool.md)在 60 个 R07 短模拟负载上对照原执行器。以上只能说明选择语义的延续及历史模拟器实现开销，不能作为原版 `entry` 在 R10 原生执行器的计时对照；冻结主实验仍只有 `entry-replay` 与 `local-cost` 两臂。
