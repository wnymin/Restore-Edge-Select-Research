# R09：恢复边界的选点时间、质量与预算

**2026-11-24 拟定；2026-11-25 启动。** 本轮由我方执行，不预设有外部协作者或独立盲验。承接 [R08 的反例和候选负结果](r08-takeover-results.md)：既不因 CPU 决策用时长就认定它全部暴露在关键路径，也不因 GPU 正忙就认定选点可以等到 GPU 完成。

## 一、研究问题与范围

1. **选点时间与质量：** 从冻结 `entry-replay` 出发，增加同视野复核、扩大已到达视野、少量后继联动、尾部守门各需要多少 CPU 时间？同一个快照上，增加这些工作能多拿到多少收益，会不会改坏动作？放回事件流后，有多少收益被延迟发布抵销？最终交付「搜索时间—动作质量」和「可用预算—净响应」两条曲线，不把它们混成一条。
2. **可留给选点的时间：** 在已有配置、队列和搬运状态下，统计边界结果可以晚多久才发布，以及其中多少能在不增加恢复等待的条件下给 CPU 用。给出**预设的额外搜索预算、适用分层、超时回退规则与置信边界**。如果不能认证正预算，仍交付分布和零额外预算／证据不足结论，不以样本均值代替安全预算。

固定 R08 的检查点契约、请求顺序、缓存放置、预取资格、容量、单计算槽及串行搬运。候选只能用首次进入既定窗口时可见的信息做推演，不借未来到达，不提前进入窗口，不启动未确认边界的预取。开始前钉住输入、实现和基线版本；`local-cost` 作为收益参照，`entry-replay` 作为部署决策对照，R08 完整 `entry-refinement` 作为不限时对照，离线最优只用于评价。若测试专用搜索线程与调度线程并行，只作**单列的机制对照**；不和现有 `pending` 路径混报，也不改默认执行器。

## 二、可用时间怎么测：延后发布，不改选点

### 2.1 冻结动作的因果测量

以**含原基线决策成本**的正常路径为参照。对同一恢复请求，记录首次可选时刻 $t_0$、冻结结果一般可发布的时刻 $t_b$、当前 GPU 是否真忙及剩余工作、暂存额度、RAM/SSD 在途和队列、首次可能受边界影响的预留、搬运发出／就绪、接管和 GPU 开始时刻。人为在 $t_b$ 后额外延迟发布 $d$，保持整个窗的边界序列不变。对照与干预注入同一份基线决策计时记录，避免两次 CPU 计时的抖动被误判为延迟效应；另用重复计时检验记录的敏感性。按实际事件比较两种预算：

- **事件保守余量：** 不推迟任何受影响的原预留或传输发出，不引入额外 GPU 空等。识别预取最早何时真正依赖选点，而不是直接拿「GPU 预计还有多久」当预算。
- **性能余量（主预算口径）：** 允许预留／搬运稍晚，但在固定动作下不推迟任何请求的 GPU 开始与完成，也不增加峰值暂存。记录任何预取机会变化；这不等于换边界后就一定无害。

先扫描单次延迟，再对一整个源窗按同一额外上限给**所有符合条件的决策**施加延迟，使用实际串行决策资源，验证不重复分配同一段空档。对每个输入用冻结的时间网格做扫描，在临界事件附近细化，记录「从 0 起连续通过的已测档位」和首个失败点；不默认安全性单调，也不把未测间隔说成连续保证。保存同刻先后规则和最小 0 预算见证，专门检查「GPU 还忙但预取已到发出时刻」「GPU 已空闲但无可用预取」和「搬运忙但预留竞争已发生」。

### 2.2 分层与数据口径

- **执行状态主轴：** GPU 忙／空闲 × 已有依赖就绪／有冷依赖；冷依赖再分搬运通道可发出、正被占用、容量阻塞。GPU 剩余时间保存连续值，不能只分忙闲。同时记录已到达后继数量、预算竞争是否共享对象及重叠可见性。
- **成本和已有配置：** 实测成本回填的 4B 是主统计域，16 层衍生和 4B／27B 架构代理分开；低／高压力、固定容量与候选并集临界点分别出表。至少覆盖 R08 的 B481/B482、容量负对照、尾部见证和原本已最优的点。旧窗仅作诊断与校准；同一源窗的成本、容量、压力、重复计时均不能当新样本。
- **平台：** CPU 事件模拟为主；本机若能可靠地对齐 CPU 选点、预取发出、GPU 忙闲时间，再做配对探针与探针开销对照。接口不够则报告缺口，实测成本回填仍称为模拟，不输出生产建议或真实 A/B 结论。

## 三、如何从统计结果给出预设时间预算

1. **先描述，再验收。** 各层报告单决策余量的零值比例、P05/P10/P50/P95、关键事件余量与性能余量的差、可并行的时间比例，以及整窗同时使用预算的失败率。报告源数量和源窗数量，按源窗聚合；数值小于计时粒度的点单列。初始额外预算扫描建议为 0、0.05、0.1、0.25、0.5、1、2、4、8、16、32 ms，只在校准集调整网格或增加临界点。
2. **预登记一个主预算。** 在校准集按整窗同时延后测试，选出实测成本 4B 主域较安全的网格上限，并冻结**一条**启用／回退规则和**一个**候选上限。其他情况默认零额外预算，分层预算先作探索。冻结的规则可用决策时可见的剩余计算或最早预取机会估计动态压低上限，并扣除状态采集、发布余量和不可中断步骤所需时间；估计不可靠就回退。事后时刻只作诊断。统计上限是额外预算，不包含已经完成的冻结策略决策；同时另报选点总耗时。
3. **主口径检验：每个留出源窗只记一次成功或失败。** 在该窗的预登记配置里同时施加规则允许的额外延迟；任一请求 GPU 开始／完成更晚或峰值暂存增加，该窗记失败。主域建议预注册为「失败窗比例不超过 5%，单侧 95% 置信上限验收」。分母是声明主域的全部留出窗；另报有实际启用的窗比例、其中的失败数和真正使用的预算，不能靠全程回退得出“有正预算”的结论。在可视为独立且来自声明抽样总体的 $n$ 个留出单位上，用单侧精确二项上限；零失败时上限为 $1-0.05^{1/n}$，因此 **至少 59 个独立单位且零失败**才足以支持这一档（有失败则按实算上限）。这不是“逐请求安全概率”。若要同时确认多个预算表项，要预先分配显著性或另留验证窗；不能看同一留出再降低预算并宣称通过。
4. **样本不足就缩小主张。** 公开轨迹按源或不相邻的连续区块分割校准与留出，核对原始行区间、重复和时间依赖；不能仅因不重叠就视为独立。相关性难以处理或源数不足时，仅报告这批轨迹的实测覆盖、按源敏感性和失败窗，不给 95/95 保证。可另用独立种子的预定义随机负载补足对**生成分布**的统计检验，但不能把它计入公开轨迹或生产流量的有效样本。未认证正预算时，默认 **0 ms 额外搜索**；可单列实验建议档，不称为部署预算。

## 四、时间与选点质量怎么测

从相同冻结快照，用相同候选和后续执行规则分阶段复用回放：原动作 → 同视野复核 → 扩已到达视野 → 有限后继联动；尾部守门分别消融。保留原动作和已完成且合格的最好动作，时间不够不启动不能及时结束的一步。软件时限需计入取状态、检查和回退；用真实墙钟验证超时与实际发布晚点，不把回放次数当毫秒。分别做确定性工作量档和墙钟档，暖机和轮换配对顺序；主结果至少六轮，不把轮次当独立样本。

- **动作质量曲线：** 相同快照和提交时刻，只换预算内选出的动作；按源窗报告零决策开销的均值、P95、单请求额外等待、翻转率与已认证离线缺口。只在分母为正且可认证时给缺口补回比例。
- **净效果曲线：** 实际按预算运行并发布，统计 CPU 决策 P50/P95/最大值、到点回退／超时率、预取错过率、GPU 空等、含开销均值与 P95、相对 `local-cost` 的净节省、重复尾部。改动作可能改变后续可用余量，必须闭环重测；第二节固定动作测得的安全性不等于算法安全性。
- **验收：** 机制上须对齐原基线、校验合法动作、精确恢复、预算与未来不可见；反例可用时报告保留了多少收益，缺同类见证不能当成通过。提议启用正预算必须同时通过固定动作的统计门槛，并在冻结的新留出上观察到含开销净改善、且原良好工况不超过 R08 的 +1 ms 均值／P95、保留 99% 正净节省、不新增六轮中至少四轮比 `local-cost` 多等超过 10 ms 的请求。按源窗报告净改善区间，不能以几个回归点抵扣坏窗。无正预算、可并行但无净收益、或证据不足，均可作为 R09 的完整负结果，不作为替换依据。
