| --- | --- | --- |

## 真实调度分线（2026-11-24）

以下是本机 Vulkan `llama-server` 的**强制整槽动作对照**，不是冻结选点策略接管。每个数字是同提示深恢复（1024 token）减浅恢复（512 token）；相邻 token 间隔为客户端 SSE 接收间隔，不能直接等同设备 kernel 时间。

| 编号 | 新观察 | 暂不能推出什么／后续用法 |
| --- | --- | --- |
| `R07-A06` | **目标更快、正在解码的请求更卡。** 4B／512 batch／关闭连续合批，有同行时目标首 token 中位差 −209.36 ms，但同行最长 token 间隔 +10.29 ms、整段生成 +12.24 ms；加排队后继时分别 −217.84、+13.27、+21.31 ms。无后继 4/8、加后继 5/8 个配对最长间隔多于 10 ms。 | 复现的是目标收益与同行退化可共存，不是直接复现 R08 的具体事件或其生产发生率。把同行最长间隔和目标 TTFT 分开回归，不以均值抵销。 |
| `R07-A07` | **指标换个阶段，方向会变。** 同模型、同提示，开启连续合批时，最长整段间隔在有/无后继时分别改善 58.58/51.11 ms，但与恢复 RPC 重叠的最大间隔中位差反向（+11.31/+11.24 ms）。 | 交叠不证明每一毫秒由恢复导致；RPC 还包含排队与调度，批设置又分进程。用只恢复、继续算、无探针三种对照拆分，不把某一段间隔增大当整段都更慢。 |
| `R07-A08` | **旁路看到的快照不够用于精确选点。** 完整读取 `/slots` 时，16/16 个验证动作能从 `n_prompt_tokens` 看见已确认恢复的长度（0→512/1024）；只看忙闲和生成进度则漏掉它。两个活动槽的任务 ID 不变时，`/metrics` 能看到等待数从 0→1→2，但 `/slots` 仍只有活动槽，未给待选请求的候选和依赖。两次同步探针约 189 ms，且使目标首 token 中位再等 187–198 ms。 | 不用事后 `cache_n` 或完成时间补为在线特征。若不能辨认精确检查点、暂存/搬运状态和待并批队列，就不在这个接口宣称已运行真实 `entry-replay`。 |
| `R07-A09` | **衍生模型能加载不等于能稳定流式服务。** 16 层留出初次热身曾返回 58 个同行片段后，没有完整流结束；同一服务进程日志出现内容解析告警和任务取消。 | 同协议正式运行 21/32 个有同行尝试失败；同一八个同行提示单独运行，无恢复或其他请求时 16 层仍失败 5/8、4B 0/8。故不能把错误归给恢复或队列。尚未区分衍生模型、输入、输出解析，完整延迟子集不能证明可用性。 |
| `R07-A10` | **流式片段不总是一 token 一条。** 观察者对照的第 3 块，七种动作均由服务端报 64 token，但客户端只有 63 个有内容或 token ID 的 SSE 片段。 | 这块只能读客户端可见间隔，不插造缺失 token 的时刻。排除这一块后，恢复与续算的主要方向不变；以归档的七块敏感性结果复核。 |
