# 动态状态如何改变混合模型的恢复边界选择

B 组在单计算槽、单传输队列、固定缓存放置的 CPU 模拟中检验了三个问题。相同搬运成本下，改变请求的到达间隔、共享前缀或队列已占的暂存空间，可以反转浅恢复的收益。在线门控能保留受压留出场景中的均值收益，并减少窗口推演。当前留出样本里，按硬件档位或仅按独占成本筛选也拿到了相同的零开销均值，动态状态的新增价值主要表现为少做推演。

后续的[选点开销迭代](dynamic-cpu-compact.md)沿用这轮的门槛，在另一批窗口验证实现开销和选点等价性。

后续研究还包括[搬运下界及其代价](dynamic-cpu-transfer-bound.md)、[离线双资源下界](dynamic-cpu-oracle-resources.md)、[相同状态分支合并](dynamic-cpu-oracle-dominance.md)和[未来到达不可见时的差距下界](dynamic-cpu-unseen-arrival.md)。

## B1 · 固定历史，只改一次边界

每条轨迹先按 `local-cost` 跑一遍。在请求首次选点时记录两条分支共有的快照，再从相同输入开始复现历史，只替换目标请求的边界。目标之后继续执行 `local-cost`，并逐项核对其他请求的边界都相同。差分报告目标、更早和更晚请求的完成时间。正数表示改选后更快。请求无随机生成，输入、窗口编号、系数和预算都保存在表中。

下表是同一合成三请求轨迹的配对干预。仅 SSD 搬运放慢 16 倍，目标请求 C 由 1,152 改为 576 token。各行都与同预算的参考行相比，仅更改一项。续算、传输与并发降速沿用归档成本模型。

| 预取预算 | 单项变化 | 剩余额度或重叠 | C 完成提前 | 全部请求完成时间之和减少 |
| ---: | --- | --- | ---: | ---: |
| 144 MiB | 参考，C 在 1 ms 到达 | 58.875 MiB，浅恢复放不下 | −200.05 ms | −200.05 ms |
| 144 MiB | B 的一块 18 MiB KV 在设备上已有副本，C 的对象不变 | 76.875 MiB，浅恢复可预取 | +34.57 ms | +8.21 ms |
| 160 MiB | 参考，C 在 1 ms 到达 | 74.875 MiB，可覆盖约 1,191.53 ms | +34.57 ms | +8.21 ms |
| 160 MiB | C 改在 600 ms 到达 | 余量缩到 606.12 ms | +34.57 ms | +8.21 ms |
| 160 MiB | C 改在 1,000 ms 到达 | 余量缩到 206.12 ms | −12.20 ms | −33.45 ms |
| 160 MiB | C 与 B 共用前缀，仍在 1 ms 到达 | 浅边界复用 18 MiB 预留 | −214.35 ms | −239.92 ms |

容量放得下只是第一道条件。144 MiB 的容量干预中，C 提前 34.57 ms，同时早先的请求合计慢了 26.37 ms。共享也会改变**原候选**的代价，160 MiB 共享干预里，按浅候选节省的字节单独判断会错过这一点。

百炼 Trace A 第 107、108、112 窗另筛选可重叠、已有共享和尚缺额度的案例。在同一布局与成本下，每类保留收益最大的可用改选，以及近似评分最乐观的无收益改选。以 107 窗、RAM 与 SSD 同为 12 倍为例，SSD 放置下改请求 257 可让它提前 157.10 ms，早先请求合计慢 13.86 ms，后续请求合计提前 10,840.00 ms。另一个配置下，改请求 344 的快照估计为快 28.72 ms，实际目标慢 48.92 ms，后续也合计慢 244.58 ms。逐行的配置和状态见[配对干预 CSV](../../evidence/dynamic-cpu-interventions.csv)。这些案例按机制筛选，行数不能用来估计生产发生率。

## B2 · 在线门控

状态门控在候选首次进入窗口时运行。它先计算各候选的可见增量搬运与不可覆盖等待：从增量工作中扣除就绪对象和可以接管的在途对象，再考虑传输积压、前面请求剩余计算和当前额度。只有估计领先且能直接占用已就绪对象、无需新额度或搬运的更深边界可以直接采用。出现可见收益或容量、共享、积压风险时，交给现有两至三次推演的预算搜索。其余请求沿用逐请求基线。直接改选是启发式，未得到窗口最优证书。

所有推演都只看已经到达的请求，至多纳入目标之后四个请求。前方使用已提交的边界，目标之后暂用各自的 `local-cost`。本次统一比较均值目标，门控、固定窗口和自适应筛选使用现有的窗口增益门槛，每个可见请求平均改善须超过 1 ms。`entry` 沿用其原有正收益门槛。各策略均未设单请求损失上限，逐请求损失单独报告。

只在 SSD 1、11、12 倍的 108、112 窗校准，共 144 个配置。候选门槛为 0.25、2、10、50 ms。先选零开销均值收益最大者，平手时取推演数更少者。动态门槛冻结为 **0.25 ms**，独占成本门控为 **50 ms**，硬件筛选在 **11 倍及以上**执行固定窗口策略；另做保持 0.25 ms、移除动态特征的消融。使用 16 倍以及 RAM/SSD 同时受压的配置作为整组硬件留出，它们从未参与选参。冻结参数和输入哈希见[配置记录](../../evidence/dynamic-cpu-frozen.json)。

## B3 · 留出验证

三份公开轨迹各取 SSD 第 109–111 窗及双路径第 120–121 窗，交叉 SSD/混合放置、原始/四分之一到达间隔、128/384 MiB 预算与 1/11/12/16 倍成本，共 480 个配对配置。每组沿用同一套请求、布局、候选、事件和成本。对照包含 `local-cost`、固定启用四请求窗口的搜索、按硬件档位切换、`entry`、已有自适应筛选的均值版本、两种静态门控和动态门控。

先跑零开销闭环，固定选点独立复播并比较逐请求完成时刻，再跑一遍用本机 Python 实测选点时长阻塞决策、推进模拟时钟的版本。决策耗时是每个配置中所有选点时间的总和。均值和 P95 在配置内统计再等权聚合；单请求损失按配对实例统计，跨配置重复的请求不是独立样本。实测耗时有调度抖动，亚毫秒净差只作本机观察。

每个 `local-cost` 的零开销均值与[归档离线表](../../evidence/adaptive-trace-oracle.csv)逐项匹配。归档搜索的下界保持有效；若新策略提供更好的完整可行序列，取更紧的上界。本批有 **466/480** 个配置已认证精确离线最优，其余保留区间。接近率按同组等权平均的均值和离线区间计算。零可降空间标为无可降空间。离线目标是无决策耗时、无单请求上限的平均响应；CPU 模拟指标为到达至预填充完成时间。

下表以 `local-cost` 为基线。接近率使用零开销均值，P95、净收益和逐请求损失来自注入决策时长的回放。

| 搬运压力 | 配置数 | 动态门控零开销均值改善 | 含开销净改善 | P95 改善 | 慢超过 10 ms 的实例 | 离线接近率 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| SSD 1× | 72 | 0 ms | +0.006 ms | +0.003 ms | 0 / 5,016 | 无可降空间 |
| SSD 11× | 72 | 105.39 ms | 105.29 ms | 176.93 ms | 1 / 5,016 | 100% |
| SSD 12× | 72 | 636.64 ms | 636.35 ms | 1,225.51 ms | 0 / 5,016 | 100% |
| SSD 16× | 72 | 558.17 ms | 557.75 ms | 1,073.66 ms | 54 / 5,016 | 98.96%–99.55% |
| RAM 与 SSD 1× | 48 | 0 ms | +0.003 ms | +0.003 ms | 0 / 3,224 | 无可降空间 |
| RAM 与 SSD 11× | 48 | 732.14 ms | 731.96 ms | 1,257.40 ms | 28 / 3,224 | 99.48%–100% |
| RAM 与 SSD 12× | 48 | 717.65 ms | 717.47 ms | 1,231.08 ms | 28 / 3,224 | 99.08%–100% |
| RAM 与 SSD 16× | 48 | 710.45 ms | 710.09 ms | 1,215.71 ms | 30 / 3,224 | 96.86%–99.99% |

360 个受压配置上，动态门控、固定窗口、`entry`、两种静态消融和硬件分档的零开销均值逐配置相同。动态门控共推演 4,600 次，比固定窗口的 9,763 次少 **52.9%**，比 `entry` 的 6,595 次少 **30.3%**，比独立校准的静态门控的 5,296 次少 **13.1%**。与固定窗口相比，注入实测开销后平均每个配置多改善 0.085 ms。与 `entry` 和独立校准静态版相比，净差分别为 −0.032 ms 和 +0.001 ms。前者在 360 对中有 311 对更快。这些亚毫秒数值受本机计时影响，不支持动态门控带来稳定净提速的主张。

1 倍成本下，120 个配置的 `local-cost` 均达到离线最优。动态门控没有做任何推演，但仍有构造快照和评分的成本，此时保留逐请求基线即可。受压时，相对基线的百毫秒收益足以覆盖推演成本。若已经采用 `entry` 或静态门控，这批证据只支持动态门控降低推演次数。双路径 16 倍组的最慢单请求额外等待约 18.48 ms，均值优化需要与逐请求保护分开验收。倍率只表示模拟输入的成本放大，应用边界也限于本次执行器、窗口和目标。

## 复现

从仓库根目录使用 Python 3.12 或 3.13。已有公开轨迹时用 `--trace-dir` 指定目录。程序按[百炼数据清单](../../../data/bailian-manifest.json)核对文件大小和 SHA-256，不需要权重、GPU 或 A 组样本。合成案例可加 `--synthetic-only` 独立运行。

~~~sh
python -m scripts.data.fetch_bailian
python scripts/check_fixture.py
python -m scripts.cpu.dynamic.study_dynamic_cpu_interventions --out outputs/dynamic-cpu-interventions.csv
python -m scripts.cpu.dynamic.study_dynamic_cpu_holdout --frozen outputs/dynamic-cpu-frozen.json
python -m scripts.cpu.dynamic.study_dynamic_cpu_holdout --frozen outputs/dynamic-cpu-frozen.json --out outputs/dynamic-cpu-holdout.csv
~~~

从归档冻结文件重跑时，把最后一条的 `--frozen` 改为 `docs/evidence/dynamic-cpu-frozen.json`。输入沿用 [Vulkan 4K 续算表](../../evidence/prefill-vulkan-4k.json)、[搬运成本](../../evidence/load-staged-ssd-profile.json)和[并发降速](../../../configs/overlap-observed-upper.json)。每个轨迹窗口取前 256 条建立缓存，后 96 条中保留不超过 3,584 token 的请求。没有随机采样。CPU 策略和取样基于第三阶段提交 `c3def50`。

仓库中的 CSV、JSON 和 Python 文件统一检出为 LF 换行，以保持冻结文件中的字节哈希在 Windows 和其他系统上一致。若旧检出曾将 CSV 转为 CRLF，可在确认该文件没有本地修改后重新检出 `docs/evidence/adaptive-trace-oracle.csv`。输入校验仍比较原始字节，公开轨迹也继续按上游清单严格核对大小和 SHA-256。
