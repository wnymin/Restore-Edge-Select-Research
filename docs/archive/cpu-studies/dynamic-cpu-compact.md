# 降低动态选点的计算开销

后续在同一执行器中对照了[保持原选点的 `entry` 提速](dynamic-cpu-entry.md)。

上一轮的动态门控减少了推演次数，注入选点耗时后仍未稳定快过 `entry`。这轮沿用冻结的 **0.25 ms** 门槛、候选排名和推演预算，减少选点前后为搜索准备数据的成本。

## 计算方法

分析校准窗口发现，动态版除了回放，还在选点时重新插值了续算表，并为每个候选构造一份完成时刻下界向量。实验模式启用三个改动：

- 当搬运成本可知、费率恒定且沿用单传输通道时，直接从已构建的对象搬运表和续算表读取时间。传输与计算发生重叠时仍按原事件模型更新剩余工作。
- 同一快照中的到达龄和在途余量每次决策只算一次。
- 优化均值时，搜索判断所需的是完成时刻下界的总和。若窗口中有 $m$ 个从目标开始的未完成请求，某候选比基线多 $Delta$ ms 的续算，则这 $m$ 个请求的纯计算下界都增加 $Delta$，更早请求的下界不变。候选的总下界由基线总下界加 $m\Delta$ 直接得到。排序和剪枝继续使用有理数。

这条路径只用于带门控、优化均值的单槽搜索。带单请求保护的策略仍逐项比较完整的下界向量。有估计误差、未知实际搬运时间或时变费率的配置会拒绝启用这条路径。

## 验证口径

先复查上一轮 480 个留出配置，要求新旧动态版的边界、完成时刻、推演数、搜索证书和其余模拟输出全部一致。再用未参与选参的百炼第 68、70、72 窗交叉比较 `local-cost`、`entry`、原动态版和本轮实现。三份轨迹、两种放置/间隔组合、两档预取预算、SSD 或双路径受压、四档成本，共 288 个配置。门槛沿用上一轮校准值。

每个配置先在固定零开销事件序列上记录三次选点耗时，再做三次把实测耗时注入模拟时钟的配对回放。每次用预先固定的种子打乱策略顺序，按配置取配对差的中位数后等权聚合。离线搜索用零开销可行序列作上界，每配置最多扩展 32 个节点，并重新回放达到上界的计划；上下界不等时保留区间。

两轮共 **768 个配置**的新旧动态版零开销结果逐项一致。新留出中的 **216 个受压配置**平均每配置的选点耗时如下，包含该配置内全部请求的选点时间。

| 策略 | 选点用时 | 推演次数合计 |
| --- | ---: | ---: |
| `entry` | 4.39 ms | 4,317 |
| 原动态门控 | 4.76 ms | 3,551 |
| 合并下界与缓存查表 | 3.88 ms | 3,551 |

与原动态门控相比，选点计时下降 **18.4%**。与 `entry` 比较，零开销平均响应在 288 个配置中的 287 个相同，另一个多等 38.06 ms。计入开销后，在受压组的 216 个配置里有 87 个较快，平均慢 0.16 ms。离线搜索在 288 个配置中认证了 177 个最优，其余保留区间。例如，双路径 32 倍时，动态版对离线可降空间的接近率为 **70.01%–100%**。这个区间较宽，反映了 32 节点的搜索上限。

## 基线恢复放不下时，检查它对后续请求的影响

在 Trace A 第 70 窗的一条反例中，128 MiB 预算只剩 62.875 MiB，`local-cost` 选中的 512-token RAM 恢复需要 65.125 MiB 新额度，只能等到队首搬运。原门控估计 512-token 恢复对当前请求快约 64.48 ms，因而跳过推演。实际回放中，从头重算确实让目标多等 127.62 ms，但更早请求合计提前 4.78 ms，之后 24 个请求各提前 131.97 ms，整条轨迹平均提前 38.06 ms。把边界单独改成 0 就能复现差值，其他选点保持相同。

补充规则只在以下条件同时成立时请求窗口推演。基线是非零恢复，目标尚未到队首，有已到达的后续请求，基线的新增额度小于等于总预算但超过当前余额。窗口仍用原有目标函数和两至三次推演的预算。在这条反例中，新规则重新选中 0，获得与 `entry` 相同的逐请求完成时刻，使用 19 次推演，对照分别为原门控 13 次和 `entry` 37 次。这是用于推导规则的机制例，单独报告。[反例快照与单次干预](../../evidence/dynamic-cpu-blocked.witness.json)

在第 69、71、76 窗的第二批 288 个配置中，补充检查触发了 241 次。其中 110 次出现在 1 倍组，零开销均值均与原门控一致。受压组额外触发 131 次，推演从 4,006 次增至 4,163 次，仍少于 `entry` 的 5,170 次。本批唯一改变闭环均值的是 Trace A 第 71 窗、SSD 32 倍的配置，相较 `entry` 的差距从 **57.95 ms** 降到 **4.96 ms**。受压组计时后相较 `entry` 平均快 0.013 ms，216 对中有 86 对较快，差距处在本机计时的亚毫秒波动内。逐请求最差额外等待约 149.49 ms，仍需要独立的服务保护条件。离线搜索认证了 142 个配置。[第二批逐配置结果](../../evidence/dynamic-cpu-blocked.csv) · [汇总](../../evidence/dynamic-cpu-blocked-summary.csv)

第二批的事后消融把窗口增益门槛从每个可见请求 1 ms 降到 0，其余规则相同。补充检查版相对 `entry` 的零开销均值原有 10 个退化、2 个改善。门槛降到 0 后，11 个差异消失，两例原先快 91.64 ms 的配置也回到相同均值。仍慢 4.96 ms 的一例里，基线所需对象已经就绪且仍处于预留中，按需搬运检查没有触发。窗口增益门槛能改变之后的排队，闭环收益需用全轨迹对照核实。[门槛消融数据](../../evidence/dynamic-cpu-threshold-ablation.csv)

## 能否进一步过滤补充检查

在补充检查上加一个筛选，只在基线的新增搬运耗时超过目标改选的估计代价时推演。固定这一条判断后，在第 65、67、73 窗另测 288 个配置。检查从 255 次降到 34 次，所有配置的零开销均值都与补充检查一致。1 倍组的 134 次检查全部跳过。受压组的选点用时由 5.01 ms 降为 4.89 ms。离线搜索在这批认证了 145 个配置。[第三批逐配置结果](../../evidence/dynamic-cpu-io-margin.csv) · [汇总](../../evidence/dynamic-cpu-io-margin-summary.csv)

回看机制例，额外筛选保住了第 70 窗的 38.06 ms 改善，却丢掉了第 71 窗的 52.99 ms 改善。第 71 窗的第 285 个请求自身只需新增 4.09 ms RAM 搬运，但当时另有约 128.30 ms 的传输在途，预取余量也不够。仅用目标新增搬运无法判断这种跨请求代价。这条筛选保留为消融，当前结果支持使用合并下界和缓存查表降低计算成本，补充检查则适合保留为可选对照。三个留出批次均未提供对 `entry` 稳定净提速的证据。[第 71 窗反例快照](../../evidence/dynamic-cpu-io-margin.witness.json)
