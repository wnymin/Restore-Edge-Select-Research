# 怎么验证 `entry-replay` 能否用于真实调度？

历史讨论稿；本机可执行部分已按用户要求列入 [R07 真实调度分线](../r07-process/r07-live-preregistration.md)，不另开阶段、不改策略。R08 验证的是冻结执行语义下的恢复选点；拿掉这一假设后，先查反例机制是否仍成立，而不是重扫同一模拟矩阵。[调优回归清单](r08-anomaly-register.md)

| 证据层 | 建议实验 | 能回答什么／不能回答什么 |
| --- | --- | --- |
| **真实 GPU 的小型因果实验**（先做） | 从仓库已有两槽和真实状态暂存路径起步。固定提示、初始缓存、搬运和执行器，只切换 `local-cost`、冻结 `entry-replay` 或一个指定边界。安排“已有解码的短请求＋尝试恢复的长请求＋排队后继”，配对改启动时差、额度（并集临界线两侧）、是否允许 prefill 和 decode 同批。先单因素，再只交叉有信号的因素。 | 看被影响的是目标 TTFT、已有请求的 token 间隔，还是后继排队；找出搬运或续算实际是否压到关键路径。若接口只允许整槽恢复，不把它当作细粒度选点的端到端验证。 |
| **真实调度器影子验证**（扩大样本） | 在调度决策前记录当前可见队列、批次 token 预算、暂存预留与在途状态，后续才记录阶段时间。冻结策略旁路输出动作与开销，不改变服务。按有无联动、接近门槛、轻/重负载分层；抽取动作分歧与近似平局做短窗口强制边界配对。 | 测可观测性、可执行率、预测方向与开销。影子日志只观测真正执行的动作，不能用同一条日志把另一动作的 TTFT 当实测。若只能影子运行，结论止于此。 |
| **同一真实调度器闭环 A/B**（验证可迁移） | 只有能执行相同精确检查点候选时才开展。对固定请求时序做开环重放，保持模型、初始缓存、调度配置和容量一致；A/B 交替执行，按完整会话/负载块复位，避免两个策略共享队列和缓存。先单模型，将有效工况在另一种批次预算、独立流量来源与可兼容的模型或设备上留出验证。优先轻载/近饱和两档及临界容量两侧；把抢占等耦合因素留给第二轮。 | 在生产近似路径上比较系统净收益与尾部代价。小窗的强制计划只能给“已执行候选中的最佳”参照；长窗说相对基线的配对差，不借用 R08 的离线最优当真实调度最优。 |

## 什么样的结果才提高置信度？

- **验收分开做。** 先检查缓存正确性、候选实际可执行和线上只用决策时可见信号，再比较计入遥测/选点/回退后的净收益。保留 TTFT（首 token）、ITL（相邻 token 间隔）、P95/P99、吞吐和 SLO 达标率，并单列同一请求的损失；超时、丢弃、回退均纳入，不只统计成功请求。
- **用负对照辨别因果。** 对照没有冷预取机会与基线无收益空间的工况；记录排队、预留、开始搬运、可用、实际消费、计算获批、首 token 各时间点。阶段不能可靠拆开就标未归因。合理的首个实验是复用本地 4B，先重现“平均更快、某个请求更慢”的因果链，再考虑更大 GPU 或不同后端。
- **先定容忍度，再开独立留出。** 按目标服务的 SLO 冻结均值/吞吐收益门槛和尾部非劣预算，不把模拟的 10 ms 自动当生产标准。以流量块/会话窗口为配对统计单位，区分同输入重复的测量误差和新输入的泛化误差；对独立块报区间，样本太少或区间跨门槛就记未定。不同模型或时段不混成一个总平均来通过验收。历史反例仅用于调试，不参与最终验收。
