# R08 反例登记：以后调优先查这里

本页是冻结 `entry-replay` 的回归清单，不是调优结果。不修改 R08 的离线目标和已冻结阈值。与 [R07 反常点](../r07-process/r07-anomaly-register.md) 对照；`R08-Axx` 是见证编号，不是任务编号。

| 编号／优先级 | 见证与已观察到的问题 | 以后怎么用 |
| --- | --- | --- |
| `R08-A01`／先查：均值收益掩盖个体损失 | 主留出 165/864 个配置有同一请求至少四轮比 `local-cost` 多等超过 10 ms，覆盖 11/12 个源窗；均落在 281 个已认证有可省空间的配置内。最坏点 Trace B 481／27B 架构载荷／16×／512 MiB，六轮都是请求索引 15、16 超阈；最坏单轮 36.253 ms，不计选点开销仍有 36.105 ms 的最大个体损失，而该窗零开销均值仍省 682.367 ms。全实测成本回放也有 16/168 个超阈配置，均为 4B 压力点。 | 不只报均值与总体 P95：保留配对请求、受损类别和服务阶段。先做单动作干预查谁让谁等待；该 R08 最坏例尚未完成逐请求归因，不能直接假定是后继预取或搬运抢占。对照已有 [R07 单动作见证](../../evidence/r07-tail-witness.json)。 |
| `R08-A02`／次查：四步视野遗漏已到达的请求 | Trace B 481／4B／12×／176 MiB，21 个冷候选均可单独装下；目标索引 7 原选 `1024`，只纳入更多已到达的请求即翻到 `512`。闭环仅强制这一动作改善整窗均值 13.251 ms（约占可省空间 40.1%）；该容量组总体接近率仍为 99.56%。 | 固定执行器预取窗口和其余配置，比较短/长视野，测实际选点 CPU 和净收益。扩大视野是诊断，不是默认修复；已到达信息与未来信息必须分开。 |
| `R08-A03`／次查：扩视野仍可能修不好联动 | Trace B 482／27B 架构载荷／16×／384 MiB，整窗比离线最优多 252.670 ms（可省空间的 13.91%）。把视野扩大到全部已到达请求仍选 `1024`；允许对两个已到达后继（索引 17、28）联合试跑才翻成 `512`。仅强制当前步，均值改善 222.191 ms，仍有未解释差距。 | 次序上先测联动从哪来，再考虑只检查少数后继。联合试跑没有证明真实在线净收益，更没有证明应把策略扩为全队列搜索。 |
| `R08-A04`／必留负对照：能预取不等于有选点收益 | Trace B 481／27B 架构载荷／16×，176→180 MiB 时，能单独装下的冷候选从 0→14，实际预留从 0→13，但两点基线均最优。384 MiB 则测得该窗 681.075 ms 的可省空间，冻结策略拿到全部；未说明中间各容量连续单调。 | 真实执行要区分「可预留」「已发出」「已完成」「首 token 前实际消费」四件事。只提高预取次数不算策略变好。 |

**统计口径。** 平均缺口同时大于 1 ms 且超过可省空间 5% 的有 11 个配置（7 个 4B／12×、4 个 27B 架构载荷／16×），都来自 Trace B 481、482；固定配置组没有在两个源窗跨过该门槛。主留出 72 组中仍有 25 组未定，不能算作没有反例。同窗多容量与同配置六轮都不是新流量样本。历史 Coder 96 不纳入，按修正矩阵使用 Coder 101。

**调优使用规则。** 上述例子是回归靶点，不再作为新方案的泛化留出。先保存冻结主干与 `local-cost`；单因素干预确认机制后，才比较候选策略。候选方案必须同时报告均值净收益、个体退化或 SLO、决策耗时和无空间负对照；不能只修已知样例，也不能用总收益抵销尚未声明预算的尾部退化。
