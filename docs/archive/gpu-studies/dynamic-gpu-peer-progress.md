# GPU 组：同行进度与恢复选点

本轮做[分工 A1](../../work-plan.md#a-组需要-gpu-验证的研究任务)的机制探索：在同一设备和同一候选边界下，只改变同行何时开始，观察「用驻留浅前缀」与「从 SSD 冷恢复较深前缀」的相对收益是否改变。选择 1,024 → 1,152 token，因为归档中单跑偏向驻留，而同行在途时按两项响应之和偏向深恢复；同时减少的总响应曾伴随目标变慢。512 → 1,536 的归档是深恢复本来就更快的参考，不纳入本轮扫参。

## 配对设计

- RTX 4060 Laptop 8 GiB，驱动 595.97，Qwen3.5-4B Q4_K_M，llama.cpp b10923（8a56aedd6），Vulkan，两槽连续批处理。每槽上下文 4,096 token。目标与同行的总输入均为 2,560 token，同行已有 512 token 的驻留前缀。
- 同行提交后分别等 25、350、1,050 ms 再开始目标计时。每档使用同一随机种子 7201 和六个不同的提示词配对块；每块从同一个目标提示词运行有无同行和三种选点（全重算、浅驻留、深冷恢复）的六个组合，块内顺序随机。每档先丢弃一个预热块。三个时差按递增顺序分别启动服务，未随机交错，跨档均值可能受设备状态影响。
- 测量器逐条检查实际缓存长度和续算 token 数；离线分析逐块核对冷恢复读盘量与状态文件大小、六种组合完整性和返回的同一个约束贪心 token。晚时差保留决策前已结束的同行；双方在途以每个候选独立测得的客户端时间为准，属于事后诊断。分组依据仍是预设时差。
- 指标为从开始选定路径到收到一个生成 token 的响应，两项响应各从自己的开始时刻计；共同完工按两项完成时刻的较晚值计，起点为同行提交（单跑为目标开始）。收益定义为浅驻留减去深冷恢复，正数支持深恢复。

## 首轮结果

每行是六个配对块的均值，正数表示深恢复更快；同行在途的计数要求浅驻留和深冷恢复两次运行都满足。三档的无同行对照共 18 对，全部是浅驻留的目标响应更短，按档分组平均快 20.5–45.6 ms。

| 同行先提交 | 两方案均观察到同行在途 | 目标收益（ms） | 同行收益（ms） | 两项响应之和收益（ms） | 深恢复降低总响应的配对数 | 共同完工收益（ms） |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 25 ms | 6/6 | −25.7 | +164.0 | +138.3 | 6/6 | −25.7 |
| 350 ms | 6/6 | −15.2 | +105.4 | +90.2 | 4/6 | −15.3 |
| 1,050 ms | 0/6 | −6.6 | +13.3 | +6.8 | 2/6 | −6.6 |

**结果支持按负载状态区分选点，但切换取决于目标。** 25 ms 时深恢复稳定降低两项响应之和，六对中目标和共同完工却都更慢。350 ms 时同行同样在途，收益已不稳定；只知道「有同行」不能分辨这两档的稳定性。1,050 ms 时同行在选点前已完成，该组的同行响应差不能归因于选点；两项响应之和的均值由少数大差值拉高。本机小样本只提供机制线索，不估计尾延迟，也未验证在线部署收益。

**恢复接口等了多久和真正做了什么要分开看。** 25 / 350 ms 档深恢复的接口平均耗时约 574 / 253 ms，服务端报告的恢复阶段约 226 / 230 ms。两档都有经核对的冷读，但接口耗时扣除服务端恢复阶段后的差值没有细分为排队、同步或传输。一个可检验的解释是深恢复推迟目标的入批时点，使同行更早完成。下一步加入「保留浅前缀，按独立校准的时长延迟提交」对照，记录实际入批时刻；若同样改善同行，说明至少部分收益可由推迟入批解释。之后再在新种子和不同同行剩余工作量上比较「仅用独占成本」「仅看同行是否活跃」「估计同行剩余工作」三个规则。运行结束后的重叠和响应只做诊断。
