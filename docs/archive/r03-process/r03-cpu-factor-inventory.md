### 最大单请求损失的归因

低估组最大损失来自 holdout-checkpoint-+0-+0 第 0 轮，FIFO 为 A、B、D、C。计时注入后，准确估计与低估组的 C 都从零开销时的重算改为 1152，D 仍分别选择 0 和 576。低估组该轮累计选点耗时反而少 0.6684 ms，新增等待不能解释为 CPU 直接耗时。

固定 A、B，重放 D 与 C 的四种组合，仍使用原到达和实际成本，关闭耗时注入：

| D 边界 | C 边界 | C 完成时间（ms） |
| ---: | ---: | ---: |
| 0 | 0 | 46 |
| 576 | 0 | 62.25 |
| 0 | 1152 | 59 |
| 576 | 1152 | 79 |

固定计划中，D 改选对 C 的额外等待随 C 自身边界从 16.25 ms 增至 20 ms。第 0 轮中的 41.282 ms 仍大于这个固定动作效应；同一锚点八轮动作相同，最差逐请求差却在约 20.34–41.28 ms 间波动。说明还存在执行时序差异，归档未记录逐决策注入量和逐对象事件，无法唯一复原该轮的临界事件。最大值只作为该回放的观察值。

~~~python
import json
from scripts.validation.study_r03_estimate import Trigger, ROOT, read, F

case = next(x for x in read('r02-cpu-inputs.json')['cases'] if x['id'] == 'holdout-checkpoint-+0-+0')
model = json.loads((ROOT / 'configs/qwen3.5-4b.json').read_text(encoding='utf-8-sig'))['models'][0]
exp = Trigger(case['trace'], model, F(case['capacity_bytes'], 1 << 20))
assert [q['id'] for q in exp.requests] == ['A', 'B', 'D', 'C']
for d in (0, 576):
    for c in (0, 1152):
        result = exp.run('fixed', boundaries=[0, 1152, d, c])
        print(d, c, result['completion_ms'][-1])
~~~


### 固定决策延迟的同刻见证

在同一异常案例中，替换测试进程的选点计时读数，给每次选点注入相同的精确延迟。执行器与成本表保持原样。0 ns 时两种估计均让 C 重算。仅 1 ns 已使两种估计都改选深边界，C 的两个 KV 块走预取，但检查点走队首按需。延迟设为 1 ms 时动作不变，C 的三个对象均不再为 C 重搬，完成时间反而下降。这表明微小决策耗时可切换事件分支，同一动作也不决定同一搬运路径。此处复现了不连续机制，原计时异常轮仍不能从已保存的汇总耗时唯一重建。
