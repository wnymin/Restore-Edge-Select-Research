# 真实 GPU 服务：保留已驻留前缀或恢复更深边界

主问题：当较浅的前缀状态已在目标槽，是否值得放弃它，从文件恢复更深的状态来少算一些 token？这个决策同时改变候选恢复成本和加入批处理的时机。入口剪枝用于省决策 CPU，不能据此主张这里的真实推理收益。

## 物理对照

本机 RTX 4060 Laptop，完整 Qwen3.5-4B Q4_K_M，Vulkan，两槽连续批处理。固定目标和同行总输入为 2,560 token。每组将同一提示词分别做全重算、使用目标槽内已有的浅前缀、从首次读取的状态文件恢复深前缀。比较 512／1,536 与 1,024／1,152 两组边界。另交叉同行是否在执行；有同行时，目标约在其提交 150 ms 后开始决策。每组预热后做八个配对块，各块内部随机换顺序。每个条件校验实际缓存 token 数，首次读取及热状态通过卷读量核对。准备驻留状态、保存检查点均在计时前，模拟既有状态；不测为保留浅前缀额外付出的容量或生成成本。

每组前四块用于校准，后四块为留出。隔离基线按单跑目标平均响应选边界。同行条件下，实验策略按校准块的两项合计响应选候选；仅当该候选在至少四分之三的校准块里胜过隔离基线时才切换。另比全重算、固定选驻留前缀、固定恢复最长可用前缀。留出是从配对实测中按冻结规则取读数；不在连续生产轨迹上闭环运行。

目标响应从开始恢复或提交到收到一个生成 token 的响应，包括排程与接口耗时。记录两项响应之和、两项全部完成的时刻，以及服务端报告的 prefill 时间；后者也不是纯 GPU kernel 时间。小样本只报告配对方向和均值，不据此声称 P95、吞吐或生产部署收益。

## 留出结果

下表为每个条件四个留出块的均值。三种边界都在同一提示词上运行。共 96 条有效实测；16 个配对块各自的六个条件都返回了相同的单个约束贪心 token，这不检验长输出的等价性。原始读数见[配对数据](evidence/gpu-boundary-resident-trials.csv)，各基线与规则见[结果汇总](evidence/gpu-boundary-resident-summary.csv)。

| 驻留／冷恢复边界 | 同行 | 指标 | 全重算 | 用驻留前缀 | 冷恢复 |
| --- | --- | --- | ---: | ---: | ---: |
| 512／1,536 | 无 | 目标响应（ms） | 970.3 | 789.8 | **512.6** |
| 512／1,536 | 有 | 目标响应（ms） | 1,611.8 | 1,463.0 | **1,195.4** |
| 512／1,536 | 有 | 两项均完成（ms） | 1,762.7 | 1,613.9 | **1,346.3** |
| 1,024／1,152 | 无 | 目标响应（ms） | 1,060.8 | **662.6** | 714.1 |
| 1,024／1,152 | 有 | 目标响应（ms） | 1,708.3 | **1,375.4** | 1,411.9 |
| 1,024／1,152 | 有 | 两项均完成（ms） | 1,859.2 | **1,526.2** | 1,562.6 |
| 1,024／1,152 | 有 | 两项响应之和（ms） | 3,287.7 | 2,820.8 | **2,683.6** |

**多恢复的 token 数影响恢复能否回本。** 多恢复 1,024 token 时，较深边界比驻留前缀的目标响应分别少 277.2 ms（35.1%）和 267.5 ms（18.3%），各四个留出块方向一致。仅多恢复 128 token 时，单跑恢复调用平均用 79.2 ms，服务端 prefill 少报约 60.9 ms，最终目标响应慢 51.5 ms。单靠“最长前缀”或“优先用驻留前缀”都会在某类候选上选错；两组边界也同时改变了驻留与文件前缀长度，不能据此拟合通用 token 阈值。

**看到同行带来一次切换，也暴露了目标冲突。** 只在 1,024／1,152 有同行时，校准出的规则从驻留切到冷恢复。留出四块的两项响应之和都下降，均值少 137.2 ms（4.9%）；其中同行快 173.7 ms，目标慢 36.5 ms，两项结束的时刻平均也晚 36.4 ms。以目标延迟或两项完工时间来评估，这次切换没有胜过隔离基线。深恢复接口的总等待在同行时约 488 ms，服务端恢复计时约 239 ms；这组读数没有分别识别请求排队、读盘和设备传输，但给出了拆分诊断的方向。

后续候选是缩短深状态的恢复关键路径：比较按需串行恢复与提前暂存／分段恢复，在相同显存预算下单独记录排队、读盘、上传和 GPU 续算。以最快的逐请求选点为基线，先看目标 TTFT 和请求组完工时间，再在连续负载下检验 P95 与吞吐。现有数据说明有可测的优化空间，也说明单靠同行标记优化响应之和不足以充当主贡献。

## 生产环境外推：什么条件会放大差异

本机只测试了 2,560 token、一个固定同行时差和最多两个槽。短边界的受限之处尤其明显：1,152 token 的文件约 86.3 MiB，沿用 1,024 token 已驻留状态只需多算 128 token；单跑时深边界少了 60.9 ms 的服务端 prefill，却多了 79.2 ms 的恢复调用。更换硬件时，不能把这个恢复调用当作裸带宽，也不能把那 60.9 ms 当成与上下文、批大小无关的 GPU 算力常数。

生产卡的显存内部访问与主机搬运是两条路径。按 [NVIDIA HGX 规格](https://docs.nvidia.com/enterprise-reference-architectures/hgx-ai-factory-h100-h200-b200/latest/components.html)，H100／H200／B200 SXM 的 HBM 带宽分别为 3.35／4.8／最高 8 TB/s；而 [vLLM 的 H100 主机搬运微基准](https://vllm.ai/blog/2026-01-08-kv-offloading-connector)中，大块单向传输约能到 50 GB/s。GPU 升级可以让续算更快，却不会按同样倍率加速主机或存储取回。大模型又可能使每 token 续算更贵，但参数量不决定检查点大小，更不能用 MoE 的总参数量估计每 token 计算量。

以 BF16 的全注意力 KV、FP32 的 Gated DeltaNet 循环矩阵为同一假设，单条序列的逻辑状态大小取下表。按 [4B 配置](https://huggingface.co/Qwen/Qwen3.5-4B/blob/main/config.json)、[27B 配置](https://huggingface.co/Qwen/Qwen3.5-27B/blob/main/config.json)、[397B-A17B 配置](https://huggingface.co/Qwen/Qwen3.5-397B-A17B/blob/main/config.json)和 [Gated DeltaNet 状态形状](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_5/modeling_qwen3_5.py)计算。全注意力每 token 字节数是层数乘 KV 头数、头维、K/V 两份和每元素两字节；矩阵字节数是线性注意力层数乘 V 头数、K/V 头维之积和每元素四字节。略去卷积状态、分配对齐和元数据；实际精度、分块、跨卡分片或复制都需按部署重测。

| 模型 | 全注意力 KV（KiB/token） | 循环矩阵（MiB/边界） |
| --- | ---: | ---: |
| Qwen3.5-4B | 32 | 48 |
| Qwen3.5-27B | 64 | 144 |
| Qwen3.5-397B-A17B | 30 | 180 |

对于浅边界 $p$ 和深边界 $q$，若只能整状态恢复，取回的 KV 按 $q$ token 计。若布局允许保留驻留 KV 并加载缺失区间，取回的 KV 按 $q-p$ 计，但仍需要深边界的循环状态，不能把该矩阵按 token 差分。异步恢复的回本条件是节省的 GPU 续算时间超过暴露在关键路径上的搬运时间和新增排队、同步及争用代价。

下面用单卡 Qwen3.5-27B 做敏感性估计。假设已锁页 RAM 到 GPU 有效带宽 40 GB/s，SSD 到主机 5 GB/s。SSD 路径按读盘再上传串行计算；表中不计排队、解包、同步或预取覆盖。续算列假设当前边界附近每秒有效处理 5,000–20,000 token，只用作扫参。实际应直接测同一完整提示从两个边界继续的时间差，再反推边际速度。

| 边界 | 恢复方式 | 逻辑状态（MiB） | RAM 上传（ms） | SSD 串行恢复（ms） | 估计省下的续算（ms） |
| --- | --- | ---: | ---: | ---: | ---: |
| 1,024 → 1,152 | 整状态 | 216 | 5.7 | 51.0 | 6.4–25.6 |
| 1,024 → 1,152 | 缺失 KV 和深边界矩阵 | 152 | 4.0 | 35.9 | 6.4–25.6 |
| 8,192 → 12,288 | 整状态 | 912 | 23.9 | 215.2 | 204.8–819.2 |
| 8,192 → 12,288 | 缺失 KV 和深边界矩阵 | 400 | 10.5 | 94.4 | 204.8–819.2 |

例如在边际速率 10,000 token/s 时，短边界只省 12.8 ms，整状态从 RAM 上传后的理论余量约 7 ms，很容易被固定等待吃掉；长边界可省 409.6 ms，串行 SSD 整状态的理论余量约 194 ms，只搬缺失 KV 和深边界矩阵后约 315 ms。若边际速率升到 20,000 token/s，长边界从同一 SSD 串行整载也会略慢于续算，增量恢复仍有余量。这些是受假设约束的单请求关键路径差值，不能直接读成生产 TTFT 或吞吐。

最值得验证的情形是**长共享前缀、深边界 GPU 未命中、同时有足够并发让部分搬运与计算重叠**。更大的显存还可能降低 GPU 未命中频率，抵消单次恢复优化。大卡验证应先用同一引擎对比 4B 和 27B，再在固定可用缓存比例下改变共享长度、GPU 未命中比例与并发；将按需异步分块加载作为强基线，分别记录两个边界的续算差、实际传输字节、暴露等待、P95 TTFT 和吞吐。若要测 SSD，单独扫有效带宽和队列深度，避免假定系统盘读速等于服务关键路径带宽。

## 离线外推归档配对

[外推脚本](../scripts/project_gpu_boundary.py)用标准库读取已归档的 CSV，不需要运行推理或采集硬件。输入以[配对数据](evidence/gpu-boundary-resident-trials.csv)的列为接口，可来自任意设备；每个连续配对块包含全重算、浅驻留、深冷恢复与有无同行的交叉条件。脚本检查冷读和同行是否仍活跃。分析时通过 `--profile` 显式选用与输入来源匹配的配置；需要留出时用 `--from-rep` 指定起点。

对相同总长度和边界，从**无同行**的配对读取浅驻留与深恢复之间的服务端 prefill 时间差中位数 $D_{\mathrm{local}}$，避免把本机两槽排程直接套到生产环境。对每种目标状态布局重算传输字节数，再依场景计算：

$$
G = \frac{D_{\mathrm{local}}}{s} - (1-f) T_{\mathrm{transfer}} - W
$$

其中 $s$ 是目标场景相对来源测量在相同请求几何下的有效续算加速比，$f$ 是搬运被其他计算覆盖的比例，$W$ 是新增排队、同步等暴露等待的情景参数。$G>0$ 表示深恢复预计节约关键路径时间，其他情况选驻留。并发实测的响应差保留作对照，报告中的 `flip` 以来源测量的单跑目标响应选点为参照。

| v1 情景 | 续算加速比 | RAM 上传（GB/s） | SSD 读盘（GB/s） | 搬运覆盖 | 新增等待 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 有利于恢复 | 2 倍 | 50 | 7 | 50% | 0 ms |
| 参考 | 4 倍 | 40 | 5 | 0% | 10 ms |
| 不利于恢复 | 8 倍 | 25 | 3 | 0% | 30 ms |

这三个场景**是敏感性假设**。范围是三个固定情景的最小值和最大值，不是统计置信区间，也不覆盖所有生产拓扑。[归档 v1 配置](../configs/gpu-boundary-production-v1.json)对应本页的 4B 参考测量和 27B 单卡估计，每 token 64 KiB KV、每个深边界 144 MiB 循环矩阵；两段 SSD 路径在覆盖前按读盘和上传相加。换用另一来源或目标平台时，可用单独的配置表达它的字节、带宽和系数。没有对应配对的长上下文另列假设扫参。

[现有留出数据的首份自动外推](evidence/gpu-boundary-production-v1.csv)：512 → 1,536 的 RAM 整恢复在三种情景都选深边界，参考估计省 73.3 ms，情景范围为 4.7–176.7 ms；同一边界走 SSD 整恢复，参考省 23.0 ms，但范围横跨零（−79.1 至 +158.7 ms）。1,024 → 1,152 的 SSD 整恢复在参考情景预计慢 46.2 ms。这些结果比较的是同一状态下深恢复与驻留续算，不代表新策略已经在生产环境胜过强基线。
